# 应用层

## TCP（HTTP）长链接和短连接的区别

> HTTP 的长连接和短连接本质上是 TCP 长连接和短连接。HTTP 属于应用层协议，在传输层使用 TCP 协议，在网络层使用 IP 协议。IP 协议主要解决网络路由和寻址问题，TCP 协议主要解决如何在 IP 层之上可靠的传递数据包，使在网络上的另一端收到发端发出的所有包，并且顺序与发出顺序一致。TCP 有可靠，面向连接的特点。

### 1. **短连接**

- **流程**：
   建立 TCP 连接 → 发送请求 → 接收响应 → 立即关闭连接。
- **特点**：
  - 每次请求都要重新建立 TCP 连接（三次握手），用完就断开。
  - 适合请求次数少、间隔长的场景。
  - 开销大（频繁握手/挥手，浪费 CPU 和网络资源）。
- **HTTP/1.0 默认就是短连接**（除非加 `Connection: keep-alive`）。

------

### 2. **长连接**

- **流程**：
   建立 TCP 连接 → 发送多个请求/响应（共用同一条 TCP 连接） → 一定时间没活动才关闭。
- **特点**：
  - 连接建立后，多次请求可以复用，不必每次都三次握手。
  - 减少了延迟和开销，适合高频通信。
  - 需要心跳或超时机制来维持连接。
- **HTTP/1.1 默认启用长连接**（即 `Connection: keep-alive`）。
  - HTTP/2、HTTP/3 更进一步，支持一个连接上并发多路请求（多路复用）。





## TCP Keepalive 和 HTTP Keep-Alive 是一个东西吗？

这是两个完全不一样的东西，毕竟长得都不一样

> HTTP 的 Keep-Alive，是由**应用层（用户态）** 实现的，称为 HTTP 长连接；
>
> TCP 的 Keepalive，是由 **TCP 层（内核态）** 实现的，称为 TCP 保活机制；

- ## 1. **HTTP Keep-Alive（HTTP 长连接）**

  - **层次**：应用层（HTTP 协议）。

  - **作用**：让 **同一个 TCP 连接** 可以复用，避免每个资源都要重新建立和关闭连接。

  - **原因**：网页由文本、图片、视频等多个资源组成，如果每次请求都重新建 TCP，开销大。

  - **机制**：

    - **HTTP/1.0** 默认是短连接，需要在请求头里显式加上：

      ```
      Connection: Keep-Alive
      ```

    - **HTTP/1.1** 默认开启长连接，如果想关闭需要写：

      ```
      Connection: close
      ```

  - **效果**：

    - 一次 TCP 建立后，可以连续发送多个 HTTP 请求/响应。
    - 避免频繁的三次握手和四次挥手，性能更好。

  ------

  ## 2. **TCP Keepalive（TCP 保活机制）**

  - **层次**：传输层（TCP 协议）。
  - **作用**：检测对方是否还存活，防止出现“假连接”（对方死掉但连接没释放）。
  - **机制**：
    - 当长时间没有数据交互时，TCP 协议栈会自动发送 **探测报文（Keepalive probe）**。
    - 情况 1：对方正常，收到探测包会回应，TCP 连接继续保持。
    - 情况 2：对方主机崩溃或网络不可达，没有回应，TCP 会在连续多次失败后，判定连接死亡，通知应用层。
  - **特点**：
    - 在操作系统内核完成，应用层无需关心。
    - 默认探测间隔很长（Linux 默认 2 小时），通常需要手动调参数。

### HTTP协议是什么

HTTP协议是一个请求-相应协议

具有下面三个特点

**请求—响应模型**：通常由客户端主动发起。

**无状态**：协议本身不要求服务器记住前一次请求。

**消息语义统一**：通过方法、状态码、Header 和 Body 描述操作意图和处理结果。



### 请求报文

#### 组成

HTTP/1.1 请求包含：

```
请求行（请求方法 + 请求目标 + HTTP版本）
请求头
空行（表示 Header 已经结束。）
请求体（可选）
```

常见请求行是：

```
GET /users/1 HTTP/1.1
Host: api.example.com
```

服务器地址被拆成了两部分：

```
Host请求头：api.example.com
请求目标：/users/1
```

这样同一个 IP 地址和端口可以通过 `Host` 区分多个网站，也就是虚拟主机。

HTTP/1.1 客户端通常必须发送 `Host` 字段，否则服务器无法可靠判断请求的是哪个站点。



常见请求头，看一眼就行

```
Host
```

HTTP/1.0 常见方式：

```

    ↓

    ↓
返回HTTP响应
    ↓

```

```

    ↓

    ↓
请求3 → 响应3
```

```

```



### HTTP缓存

就是第一次请求后，客户端保存内容，后面的请求先看这个请求管不管用

又分为 **强缓存**和**协商缓存**

响应在 3600 秒内可视为新鲜有效。强缓存就是在有效期内直接用缓存，不问服务器。

协商缓存就是缓存已经过期，客户端问服务器资源是不是有变化。没变化：304 ，有变化：200 + 新内容

## https和http区别

> https=http+ssl但是现在ssl都被tsl所取代

- 首先说明为什么http协议不安全？**首先要知道一个安全的机制应该满足三个特性：机密性，完整性，不可否认性。**http协议通信使用明文进行通信，且没有任何其他保护措施，我们依次来看一下不安全特性。首先是机密性，由于使用明文进行通信，导致信息会被窃听泄露；然后是完整性，一段裸奔的明文在网络上传递，会被轻而易举的篡改；最后是不可否认性，由于http的请求和响应不会对通信方的身份进行确认，导致很容会被欺骗，而且用户无法察觉

  但是https使得上述三个特性都满足。

  HTTPS并非是应用层的一种新协议。只是HTTP通信接口部分用SSL（Secure Socket Layer）和TLS（Transport Layer Security）协议代替而已。

  通常，HTTP直接和TCP通信。当使用SSL时，则演变成先和SSL通信，再由SSL和TCP通信了。简言之，**所谓HTTPS，其实就是身披SSL协议这层外壳的HTTP（SSL协议位于TCP和HTTP协议之间）**。SSL主要包括几大块：

  1. 解决机密性。对请求和应答消息进行加密。公钥加密效率比较低，对称加密效率较高。因此对于密钥协商这块，使用公钥两方协商密钥，然后用密钥执行对称加密对消息加密
  2. 完整性。依靠单向散列函数实现，比如MD5或者SHA1
  3. 不可否认性。依靠数字签名来实现。

## 访问一个网页的过程

### 1. **URL 解析**

- 例：`https://www.webserver.com/dir/file`
- 拆分成：
  - 协议：`https`
  - 主机名：`www.webserver.com`
  - 路径：`/dir/file`

------

### 2. **生成 HTTP 请求**

- 浏览器根据用户行为（如输入网址或点击链接），封装成 HTTP 请求报文：
  - 请求行（GET/POST + 路径 + 协议版本）
  - 请求头（Host、User-Agent 等）
  - 请求体（POST 请求时携带数据）

------

### 3. **DNS 解析**

- 在访问服务器前，需要将域名转成 IP 地址。
- DNS 查询过程（常考点）：
  1. 先查浏览器缓存、本地 hosts、本机 DNS 缓存；
  2. 如果没有，再向本地 DNS 服务器查询；
  3. 本地 DNS 服务器逐级向根域名服务器、顶级域名服务器、权威域名服务器查询，直到得到 IP 地址。

------

### 4. **进入本机协议栈**

- 获取到目标 IP 后，浏览器把 HTTP 请求交给操作系统协议栈处理。

- 过程：

  1. 先建立 **TCP 三次握手**。

  2. HTTP 报文会被 TCP/IP 封装：

     ```
     MAC头部 + IP头部 + TCP头部 + HTTP报文
     ```

------

### 5. **网卡处理**

- 协议栈生成的报文交给网卡。
- 网卡将二进制报文转换为电信号，在物理链路上传输。
- 网卡还会加上：
  - 起始帧分界符
  - 帧校验序列（FCS）

------

### 6. **交换机转发（数据链路层，二层设备）**

- 交换机根据 MAC 地址表决定转发端口。
- 如果找不到目标 MAC，就广播给除源端口外的所有端口。
- 只有目标设备会处理该包，其余设备会丢弃。

------

### 7. **路由器转发（网络层，三层设备）**

- 路由器接收到数据帧后：
  1. 先拆掉 MAC 头，检查目的 IP；
  2. 根据路由表决定下一跳；
  3. 如果不知道 MAC，则通过 **ARP 协议** 查询 IP 对应的 MAC；
  4. 添加新的 MAC 头，继续转发。

------

### 8. **到达目标服务器**

- 报文经过多次路由器转发，最终到达目标服务器的网卡。
- 服务器协议栈逐层拆包：
  - 去掉 MAC 头 → 去掉 IP 头 → 去掉 TCP 头 → 还原出 HTTP 请求报文。
- 服务器将请求交给应用程序（如 Nginx、Apache、后端服务）。
- 应用程序生成响应报文，再按相同流程返回给浏览器。





## traceroute原理

- `traceroute` 的原理其实就是 **利用 IP 包的 TTL（Time To Live）字段** 来探测数据包经过的路由节点。整理如下：

  ------
  
  ## 1. **核心概念**
  
  - **TTL（Time To Live）**：IP 数据包头的一个字段，每经过一个路由器减 1。
    - 当 TTL = 0 时，路由器会丢弃该包，并返回一个 **ICMP 超时报文（Time Exceeded）** 给源主机。
  - **ICMP 响应**：目标主机收到数据包时，会返回 ICMP Echo Reply（如果是 ping）或正常响应。
  
  ------
  
  ## 2. **traceroute 工作流程**
  
  1. **发送第 1 个数据包**：
     - TTL = 1 → 第 1 个路由器收到，减 1 → TTL = 0 → 丢弃 → 返回 ICMP 超时报文。
     - traceroute 得到第 1 跳路由器的 IP 和延迟时间。
  2. **发送第 2 个数据包**：
     - TTL = 2 → 第 1 个路由器减 1 → TTL = 1 → 转发给第 2 个路由器 → TTL = 0 → 丢弃 → 返回 ICMP 超时报文。
     - traceroute 得到第 2 跳路由器的信息。
  3. **递增 TTL**：
     - 每次 TTL 加 1，逐跳探测路由。
     - 直到到达目标主机（收到 ICMP Echo Reply）或达到最大跳数。
  
  ------
  
  ## 3. **traceroute 的特点**
  
  - 能显示 **经过的每一跳路由器的 IP 和延迟**。
  - 依赖 ICMP 超时报文或者 UDP/ICMP Echo 回复。
  - 有些路由器可能屏蔽 ICMP，所以可能显示 `*`（超时或丢包）。



## dns的解析过程

DNS 的作用是：

> **把域名转换成 IP 地址。**

### 1. **浏览器缓存检查**

- 浏览器会先检查自己缓存中是否已有域名对应的 IP。
- 如果有，直接返回 IP，结束解析。

### 2. **操作系统缓存 / Hosts 文件**

- 如果浏览器缓存没有，再查本地操作系统缓存。

  本地 DNS 可能是：

  - 运营商提供的 DNS
  - 路由器配置的 DNS
  - 公共 DNS，例如 `8.8.8.8`

- 同时，也会检查本地 `hosts` 文件（静态映射），优先使用这里的 IP。

### 3. **本地 DNS 服务器查询**

- 如果本地没有缓存，会向本地配置的 DNS 服务器（通常是 ISP 提供的）发送查询请求。
- 这通常是一个递归查询：DNS 服务器帮你查到最终 IP 后返回。

### 4. **递归查询流程**

如果本地 DNS 服务器缓存中没有结果，它会向上层 DNS 服务器查询：

1. **根域名服务器（Root Server）**
   - 根服务器不直接给 IP，而是返回对应的 **顶级域名服务器（TLD Server）** 地址（如 `.com`、`.cn`）。
2. **顶级域名服务器（TLD Server）**
   - TLD Server 返回该域名的 **权威 DNS 服务器（Authoritative Server）** 的地址。
3. **权威 DNS 服务器**
   - 返回最终的 **域名对应 IP**。

### 5. **返回结果**

- 本地 DNS 缓存会缓存这个解析结果一段时间（TTL）。
- 浏览器拿到 IP 后，建立 TCP 连接发送 HTTP 请求。



## 所有DNS请求和回答报文使用的UDP数据报经过端口53发送

DNS 普通查询通常使用 UDP，因为查询和响应数据较小，UDP 不需要建立连接，开销低、速度快。区域传送需要同步大量 DNS 记录，为了保证可靠传输，会使用 TCP。如果 UDP 响应过大或被截断，客户端也会改用 TCP 重新查询。



## cookie和session

### 1️⃣ Cookie

- **存储位置**：保存在 **用户浏览器** 上。
- **容量**：每个 Cookie 大约 4KB，数量有限。
- **生命周期**：
  - 可以设置过期时间 → 浏览器关闭后依然存在
  - 不设置 → 浏览器关闭就消失（会话 Cookie）
- **安全性**：不安全，用户可以查看、修改或删除。
- **使用方式**：
  - 服务器发送 `Set-Cookie` → 浏览器保存 → 后续请求自动带上 Cookie
- **适合存**：少量、非敏感数据，如用户偏好、主题、语言选择等。

------

### 2️⃣ Session

- **存储位置**：保存在 **服务器** 上，每个用户对应一个 session。
- **容量**：由服务器决定，通常比 Cookie 大。
- **生命周期**：
  - 默认会话结束或超时自动销毁
- **安全性**：比 Cookie 安全，因为存服务器端，客户端只保存 session ID。
- **使用方式**：
  - 服务器生成 session → 给客户端一个 **session ID**（通常放在 Cookie 中）
  - 浏览器每次请求带上 session ID → 服务器找到对应 session 数据
- **适合存**：敏感信息、用户登录状态、购物车等。

## TCP网络编程的本质（三个半事件）

### 1️⃣ 三个事件

1. **连接事件（Connect / Accept）**
   - 对客户端：`connect()` → 试图和服务器建立连接
   - 对服务器：`listen()` + `accept()` → 等待客户端连接
   - 本质：TCP 是面向连接的，通信前必须建立一个可靠的通道（即三次握手）
2. **读事件（Read / Receive）**
   - 对客户端/服务器：`recv()` / `read()`
   - 本质：从 TCP 缓冲区读取数据
   - TCP 会保证 **顺序、可靠、完整**，应用层只负责从缓冲区拿数据
3. **写事件（Write / Send）**
   - 对客户端/服务器：`send()` / `write()`
   - 本质：将数据写入 TCP 内核缓冲区 → TCP 内核负责分段、重传、确认

------

### 2️⃣ 半个事件

- **连接关闭事件（Close / Shutdown）**
  - TCP 的连接关闭是**半双工**的：一端关闭发送，另一端仍可接收
  - 这个事件有时候被称作“半个事件”，因为它是连接生命周期的一部分，但不像前面三个事件那样频繁发生

## HTTP1.0和HTTP1.1的一些区别

最核心的区别是：

> **HTTP/1.0 默认短连接，HTTP/1.1 默认长连接。**

还有

- HTTP/1.1 强制要求 Host 请求头
- HTTP/1.1 支持分块传输（Transfer-Encoding: chunked）





## HTTP1.0和HTTP2.0有什么区别

HTTP/1.0 和 HTTP/2.0 的区别很大，因为 HTTP/2 在性能上做了大幅优化。可以从 **传输方式、头部压缩、多路复用、连接管理** 等方面来看：

------

### 1️⃣ 传输方式

| 特性     | HTTP/1.0              | HTTP/2.0                         |
| -------- | --------------------- | -------------------------------- |
| 基础协议 | 文本协议              | 二进制协议（帧/流）              |
| 数据表示 | 请求/响应都是明文文本 | 数据拆成二进制帧，更易解析和复用 |

#### 什么是二进制分帧

HTTP/2 不再把一个请求当成一整段文本发送，而是拆成多个小的二进制帧。

例如：

```
请求 A → A1、A2、A3
请求 B → B1、B2
```

这些帧可以交叉发送：

```
A1 → B1 → A2 → B2 → A3
```

接收方通过帧中的标识，把它们重新组装成请求 A 和请求 B。

避免一个请求过大，导致其他小的发不过去。

------

### 2️⃣ 连接管理

| 特性     | HTTP/1.0                          | HTTP/2.0                                      |
| -------- | --------------------------------- | --------------------------------------------- |
| 连接类型 | 短连接（每个请求新建 TCP）        | 长连接（默认复用一个 TCP 连接）               |
| TCP 复用 | 不支持                            | 支持多路复用，一个连接可并行传输多个请求/响应 |
| 阻塞问题 | 阻塞队头（Head-of-Line Blocking） | 减轻队头阻塞，每个流独立                      |

#### 什么是支持多路复用

HTTP/2 在一个 TCP 连接中创建多个 **Stream（流）**。

```
一个 TCP 连接
├── Stream 1：HTML
├── Stream 3：CSS
└── Stream 5：JavaScript
```

不同流的数据帧可以交错传输，互相不需要等待。

这就是：

> **多路复用：一个 TCP 连接同时传输多个 HTTP 请求和响应。**



------

### 3️⃣ 请求/响应效率

| 特性     | HTTP/1.0                         | HTTP/2.0                                            |
| -------- | -------------------------------- | --------------------------------------------------- |
| 请求排队 | 一个连接一次只能处理一个请求     | 多路复用，同一个连接同时处理多个请求                |
| 头部     | 每次请求重复发送完整头部（冗余） | 头部压缩（HPACK），减少数据量                       |
| 推送     | 无                               | 支持服务器推送（Server Push），提前发送资源给客户端 |

------

### 4️⃣ 安全性

- HTTP/1.0 本身不强制使用 TLS
- HTTP/2.0 通常与 HTTPS 搭配使用（实际浏览器大多要求 TLS）

------

### 5️⃣ 主要优点总结（HTTP/2.0 相比 HTTP/1.x）

1. **二进制传输** → 更高效解析
2. **多路复用** → 减少 TCP 连接数量，提高性能
3. **头部压缩** → 可以理解为把重复字段存入一张表中，后续只需要发送索引。减少冗余数据
4. **服务器推送** → 主动发送客户端可能需要的资源
5. **长连接** → 减少建立和关闭连接的开销

## TCP 与 UDP 的区别

## 核心区别

**TCP 解决“数据可靠、有序地到达”的问题；UDP 只负责“尽快把一个数据报发出去”，不保证结果。**

| 对比项            | TCP                        | UDP                      |
| ----------------- | -------------------------- | ------------------------ |
| 连接方式          | 面向连接，通信前要建立连接 | 无连接，直接发送         |
| 可靠性            | 可靠：确认、重传、校验     | 不保证送达、顺序和去重   |
| 数据形式          | **字节流**，没有消息边界   | **数据报**，保留消息边界 |
| 顺序              | 保证按序交付               | 可能乱序                 |
| 流量控制          | 有，避免接收方处理不过来   | 没有                     |
| 拥塞控制          | 有，避免网络过载           | 没有                     |
| 开销              | 较大                       | 较小                     |
| 速度与延迟        | 通常延迟更高               | 通常延迟更低             |
| 是否支持广播/组播 | 不支持                     | 支持                     |

TCP 接收端通过序列号发现数据缺失，会缓存后续乱序报文，并重复确认当前期望的序列号。发送端收到多个重复 ACK 后触发快速重传，或者等待重传超时后重新发送。缺失数据补齐后，接收端再按顺序交给应用层。

## TCP的特点

TCP 是**面向连接的、可靠的、基于字节流**的传输层通信协议。

<img src="https://cdn.jsdelivr.net/gh/luogou/cloudimg/data/202202250915293.png" alt="image-20220225091459903" style="zoom:67%; float:left" />

**面向连接**：一定是「一对一」才能连接，不能像 UDP 协议可以一个主机同时向多个主机发送消息，也就是一对多是无法做到的；

**可靠的**：无论的网络链路中出现了怎样的链路变化，TCP 都可以保证一个报文一定能够到达接收端；

**字节流**：(无边界+有序的概念)消息是「没有边界」的，所以无论我们消息有多大都可以进行传输。并且消息是「有序的」，当「前一个」消息没有收到的时候，即使它先收到了后面的字节，那么也不能扔给应用层去处理，同时对「重复」的报文会自动丢弃。





<img src="https://cdn.jsdelivr.net/gh/luogou/cloudimg/data/202202250919337.png" alt="image-20220225091921269" style="zoom:67%; float:left" />

TCP四元组可以唯一的确定一个连接。所以有一个问题比如：有一个 IP 的服务器监听了一个端口，它的 TCP 的最大连接数是多少？

首先服务器端地址确定了，源端口确定了，那么只有客户端的IP数和目标端口不确定，那不就是$2 ^ {32} \times 2^{16} = 2^{48}$。当然实际上并发的TCP连接数肯定达不到这么多：①**文件描述符限制**，Socket 都是文件，所以首先要通过 `ulimit` 配置文件描述符的数目；②**内存限制**，每个 TCP 连接都要占用一定内存，操作系统的内存是有限的。

 

## ☆TCP三次握手

<img src="https://cdn.jsdelivr.net/gh/luogou/cloudimg/data/20210822164519.png" alt="UDP 报文" style="zoom: 67%;" />

可以看到客户端和服务器端分别所处于的阶段，客户端有两个阶段，服务器方有三个。

三次握手的前两次是不能携带数据的，只有第三次可以携带数据。因为经过两次握手，客户端收到ack确认报文段之后就已经建立了连接，表明服务端的接受和发送能力是正常的，当然可以传数据。

### 为什么是三次握手

两次握手只能让服务端确认：

```
客户端能发送
服务端能接收
服务端能发送
```

但服务端无法确认：

```
客户端是否能接收到服务端的回复
```

第三次握手到达服务端，才能证明：

> 客户端确实收到了服务端的 SYN + ACK。

还有就是避免出现连接未成功的状态导致服务端先分配了资源。

比如说第一次握手，客户端发过去一个SYN，但是网络延迟了，很久才到服务器，这时候客户端认为连接不可达已经放弃这次请求，结果服务端收到以后返回ACK，这时候如果是两次握手就算成功，显然就错了。



### 初始序列号（ISN）

`ISN` 全称是 `Initial Sequence Number`，是 TCP 发送方的字节数据编号的原点，告诉对方我要开始发送数据的初始化序列号。

这个序列号是动态生成的，主要是区分不同连接的数据，也可以提高安全性，免得太容易被劫持。



### 既然 IP 层会分片，为什么 TCP 层还需要 MSS 呢？

#### MTU 和 MSS

- `MTU`：一个链路层数据包能够承载的最大 IP 包长度。
- `MSS`：一个 TCP 报文段能够携带的最大 TCP 数据长度。

就是有时候TCP一次想发送很大的消息，结果ip数据包传不过去，就把一个TCP报文段分片了，这些小片丢掉一个，就认为这个TCP段没收到，就得再发一个大的报文段，于是就浪费了时间和资源。

所以建立 TCP 连接时，双方会通过 MSS 告诉对方：

> 每个 TCP 报文段最多发送多少字节的数据，避免生成超过 MTU 的 IP 包。



### 半连接队列(SYN队列)和全连接队列(accept队列)

服务端调用 `listen()` 后，内核会维护两类连接队列。

半连接队列就是那些完成了两次握手的连接

全连接队列就是完成了三次握手的连接

#### 队列满了会怎样？

- 半连接队列满：新的 `SYN` 可能被丢弃，或者启用 SYN Cookie。
- 全连接队列满：已经完成握手的连接可能无法及时进入队列，客户端可能出现重传或连接超时。



### 什么是 SYN 攻击？如何避免 SYN 攻击？

就是攻击者发一堆握手请求，服务端发二次握手，结果攻击者不发三次握手了，服务端的半连接请求就被占满没法接收其他请求了。

#### 解决方法

1、他不发第三次握手，那就让过期时间短点儿，丢掉以前的连接

2、专业设备限制异常SYN请求

3、临时绕过半连接队列的管理（SYN Cookie），通过计算ip和端口的方式，只把正式建立的连接放到全连接队列。

### 为什么需要四次挥手

客户端想断开，得有一来一回吧，说明客户端不用收到消息了

可是服务端可能这次的还没发完，得等服务端发完了，再一来一回，表示没消息了，才能正式断开。所以得有四次。



### 为什么客户端还得等一段时间（2MSL）才能彻底关闭？

因为为了防止最后一次挥手没有到服务端，等待一个TCP包来回的时间，要是服务端的确没收到，会再给你发一个第三次握手的FIN，重新说，服务端已经发完了，要断开了。

最坏情况下：

```
最后一个 ACK 在网络中运行最多 1MSL
+
B 重传的 FIN 运行最多 1MSL
=
2MSL
```



### 谁需要等待一段时间

其实谁想断开连接谁才需要等那段时间

因为四次挥手，只有最后一次挥手是不能确定到没到的。





## TCP 黏包和半包问题

TCP是字节流传输的，没有消息边界，所以可能出现write了几次，结果另一边read全读出来了。这是黏包

半包就是wirte了一次，read一次结果没读全，还得多读几次。

### 怎么解决

主要就是解决没有消息边界的问题

1、给信息加个消息边界，比如学http \r\n\r\n，读到了就算是读完头了

2、给一次的读取固定长度，比如一次就传多少个字节。这样会浪费空间

3、消息头里记录长度（类似于http）

4、使用成熟的应用层协议



## TCP 协议怎么保证可靠传输的？

### TCP 需要解决哪些问题

IP 只负责尽力发送数据包，并不保证：

- 数据一定到达；
- 数据按照发送顺序到达；
- 数据不会重复；
- 数据在传输过程中不会损坏；
- 接收方能够及时处理数据；
- 网络能够承受发送速度。

因此，TCP 需要解决六类问题：

| 问题             | TCP 的解决机制          |
| ---------------- | ----------------------- |
| 数据损坏         | 校验和                  |
| 数据丢失         | ACK、超时重传、快速重传 |
| 数据乱序         | 序列号、接收端排序      |
| 数据重复         | 序列号、重复数据丢弃    |
| 接收方处理不过来 | 滑动窗口、流量控制      |
| 网络发生拥塞     | 拥塞窗口、拥塞控制      |





### 怎么判断数据坏没坏

#### 校验和

TCP 报文中包含校验和，用于检测传输过程中是否发生数据损坏。

接收方收到报文后会重新计算校验和：

```
校验和正确
    ↓
继续处理数据

校验和错误
    ↓
丢弃报文
```

校验和只能发现数据异常，不能修复数据。

报文被丢弃后，发送方因为收不到对应 ACK，最终会通过重传机制重新发送数据。

因此：

```
校验和负责发现错误
重传机制负责恢复数据
```



### 数据发的太快，接收方处理不过来怎么办

#### 停止等待

停止等待的工作方式是：

```
发送一个报文
      ↓
停止发送
      ↓
等待 ACK
      ↓
收到 ACK 后发送下一个报文
```

一来才有一回，太慢了



#### 滑动窗口

执行方式就类似于算法里的数据结构

里面有几个概念

##### 发送窗口

发送方需要保留所有已经发送但尚未确认的数据，因为这些数据可能需要重传。

发送缓冲区可以分为四部分：

```
已经确认 | 已发送未确认 | 可以发送但未发送 | 暂时不能发送
```

对应关系：

```
| 已确认 | 已发送未确认 | 可以发送 | 不可发送 |
          ↑              ↑          ↑
       SND.UNA         SND.NXT    窗口右边界
```

`SND.UNA`：最早一个尚未被确认的字节；

`SND.NXT`：下一个准备发送的字节；

窗口右边界：当前最多允许发送到的位置。

能确认的，窗口就可以移动了。

##### 接收窗口

收到TCP数据以后，会先放到内核缓冲区，然后再让read和recv等去读。

接收方会通过 TCP 首部中的 Window 字段告诉发送方：

> 我的接收缓冲区现在还有多少空间。

这个值称为接收窗口（rwnd，Receiver Window）

缓冲区大，那就增加接收窗口，发送方就可以发得更快了

缓冲区的数据没及时取出来，就得减小接收窗口，让发送方慢慢发



#### 流量控制

其实就是通过rwnd判断还能不能继续发了。

rwnd多大，就是说接下来发送方最大能发多少数据

这里面有一些其他概念

##### 零窗口

rwnd为0了，不让发送方继续发了，结果rwnd恢复了，通知可以继续发的报文丢失了，就很尴尬，接收方等着接收消息呢，发送方一直认为rwnd为0，一直不发。



为了避免这样一个丢失窗口更新报文的情况，发送方会启动一个坚持计时器。其实就是发送一个探测报文，如果窗口仍然为 0，发送方继续等待并再次探测。如果窗口已经大于 0，发送方恢复正常发送。





### 数据丢失怎么办

#### 重传

TCP 发送数据后，会把未确认的数据保存在发送缓冲区中。

当判断某段数据可能丢失时，TCP会重新发送。

主要有三种相关机制：

1. 超时重传；
2. 快速重传；
3. SACK 选择性确认。

#### 超时重传

发送方发送数据时，会启动重传计时器。

```
发送数据
   ↓
启动重传计时器
   ↓
在超时前收到 ACK？
   ├─ 是：取消或更新计时器
   └─ 否：重新发送数据
```

其实就是和广泛意义上的超时一个意思嘛。

超时时间称为：

```
RTO：Retransmission Timeout
```



##### RTO

这个超时时间要设置的大于网络往返时间 RTT，避免堵塞慢了，结果直接认为丢失了。但是也不能太大，避免真丢失了结果迟迟不重新传。 TCP 会根据测量得到的 RTT 和 RTT 波动情况动态计算 RTO。

##### 指数退避

要是重新发了一次结果还是超时，可能的确是网络太拥挤了，那就等待等久。第一次超时：等待 RTO 。第二次超时：等待 2 × RTO 。第三次超时：等待 4 × RTO。这就叫指数退避



#### 快速重传

因为有超时重传的存在，有可能就是判定丢失的速度很慢。那发送方先正常发送消息，然后接收方一个劲地返回ACK，返回之前的一个包，那接收方接到三次这样的ACK就知道这个没发过去，就重新发一个。快速重传是接收方每收到一个后续的包，就把之前缺失的说一遍（这就是所谓重复的ACK）。



#### 丢失会遇见一个问题

这里的问题就是每次只能说我哪个哪个段没收到，这样服务端只能传一个ACK的seq啊，也不知道后面到没到。这就不太好。

#### SACK 选择性确认

所以这里就有一个可选的功能

启用 SACK 后，接收方除了发送累计 ACK，还可以告诉发送方：

> 哪些不连续的数据区间已经收到。

例如：

```
ACK = 201
SACK = [361, 501)
```

表示：

```
201 之前的数据连续到达
361～500 这段数据也已经到达
201～360 之间的数据仍然缺失
```





### 网络堵塞怎么办

这里就不是接收方和发送方的矛盾了，变成了发送方和中间链路（比如说路由器的矛盾）。即使接收方有很大的接收缓冲区，网络中间的路由器也可能已经发生拥塞。TCP 需要根据网络情况限制发送速度。

#### 拥塞控制

维持一个拥塞窗口（cwnd：Congestion Window），发送方到底能发多少数据，取决于 min(rwnd, cwnd)



#### 怎么判断的拥塞

发生超时重传；

收到三个重复 ACK；



### 拥塞控制的具体方法

#### 经典 TCP Reno 拥塞控制

经典 Reno 拥塞控制可以分为：

1. 慢启动；

   从较小的cwnd开始发，拥塞窗口大约每经过一个 RTT 翻倍，因此属于指数增长。同时维护一个阈值，叫慢启动阈值（ssthresh：Slow Start Threshold），小于这个阈值，就是慢启动阶段，大于了，就进入下一个阶段。

2. 拥塞避免；

   进入拥塞避免后，拥塞窗口不再指数增长，而是线性增长。目的其实还是探测网络容量，又不会增长得过快。

3. 超时后的拥塞处理；

   超时一般就说明网络拥塞得很厉害了，那就别发那么多了，直接打回慢启动，并且ssthresh = 原 cwnd / 2

4. 快速重传；

   就是之前说的快速重传

5. 快速恢复。

   有快速重传就说明开始丢包了，但是还没那么严重，这时候直接降低cwnd会影响性能，毕竟发送速度取决于min(rwnd, cwnd)，所以不能直接降低cwnd到很小的值。

   快速重传是接收方每收到一个后续的包，就把之前缺失的说一遍（这就是所谓重复的ACK）。

   快速恢复的时候，

   ssthresh = cwnd / 2 

   cwnd = ssthresh + 3 × MSS（这个3*MSS）就是已经到了的三个后续包

   后面发送方每收到一个重复的ACK，就把cwnd+1，等接收方正式收到缺失的那个报文段了，就让cwnd = ssthresh。这样cwnd就不是从1开始的慢恢复状态了。

   

## TCP怎么解决性价比问题？

### Nagle 算法

这里解决的是一对小数据的问题，毕竟每个 TCP 报文至少需要 TCP 首部和 IP 首部。如果一个报文只携带少量数据，协议头占比会很高。Nagle 算法用于减少小报文数量。

```
发送一个小报文
       ↓
等待 ACK 期间又产生小数据
       ↓
先缓存
       ↓
收到 ACK 或数据达到 MSS
       ↓
合并发送
```

不过有等待的时间，所以问题也比较明显，就是增加了交互的延迟。

#### 延迟确认

ACK也算一个报文，也要 TCP 和 IP 首部。要是能让ACK发的更有性价比就好了。所以有了延迟确认。等来了一堆新数据，才把之前的报文段的ACK发出去。

```
收到数据
   ↓
是否有响应数据？
   ├─ 有：响应数据携带 ACK
   └─ 无：短暂等待
             ↓
        收到更多数据或计时到期
             ↓
           发送 ACK
```

这样同样会造成延迟。

## 服务端主动关闭连接，客户端会发生什么？

如果是服务端主动发起关闭，此时四次挥手的顺序会颠倒。那么此时客户端再向服务端发送数据时，根据TCP协议的规定，认为它是一个异常终止连接，客户端将会收到一个**RST复位**响应(而不是ACK响应)，如果客户端再次向服务端发送数据，系统将会发送一个**SIGPIPE信号**给客户端进程，告诉客户端进程该连接已关闭，不要再写了。系统给SIGPIPE信号的默认处理是直接终止收到该信号的进程，所以此时客户端进程会被极不情愿地终止。

## IP协议

IP协议（Internet Protocol，互联网协议），是TCP/IP协议栈中最核心的协议之一，通过IP地址，保证了联网设备的唯一性，实现了网络通信的面向无连接和不可靠的传输功能。

![img](https://img-blog.csdn.net/20170301092349308)

**版本**：IP协议的版本，目前的IP协议版本号为4，下一代IP协议版本号为6。

**首部长度**：IP报头的长度。固定部分的长度（20字节）和可变部分的长度之和。共占4位。最大为1111，即10[进制](https://so.csdn.net/so/search?q=进制&spm=1001.2101.3001.7020)的15，代表IP报头的最大长度可以为15个32bits（4字节），也就是最长可为15*4=60字节，除去固定部分的长度20字节，可变部分的长度最大为40字节。

**服务类型**：Type Of Service。

**总长度**：IP报文的总长度。报头的长度和数据部分的长度之和。

**标识**：唯一的标识主机发送的每一分数据报。通常每发送一个报文，它的值加一。当IP报文长度超过传输网络的MTU（最大传输单元）时必须分片，这个标识字段的值被复制到所有数据分片的标识字段中，使得这些分片在达到最终目的地时可以依照标识字段的内容重新组成原先的数据。

**标志**：共3位。R、DF、MF三位。目前只有后两位有效，DF位：为1表示不分片，为0表示分片。MF：为1表示“更多的片”，为0表示这是最后一片。

**片位移**：本分片在原先数据报文中相对首位的偏移位。（需要再乘以8）

**生存时间**：IP报文所允许通过的路由器的最大数量。每经过一个路由器，TTL减1，当为0时，路由器将该数据报丢弃。TTL 字段是由发送端初始设置一个 8 bit字段.推荐的初始值由分配数字 RFC 指定，当前值为 64。发送 ICMP 回显应答时经常把 TTL 设为最大值 255。

**协议**：指出IP报文携带的数据使用的是那种协议，以便目的主机的IP层能知道要将数据报上交到哪个进程（不同的协议有专门不同的进程处理）。和端口号类似，此处采用协议号，TCP的协议号为6，UDP的协议号为17。ICMP的协议号为1，IGMP的协议号为2.

**首部校验和**：计算IP头部的校验和，检查IP报头的完整性。

**源IP地址**：标识IP数据报的源端设备。

**目的IP地址**：标识IP数据报的目的地址

首先要充分了解网络分层的作用。网络层使用Ip协议将不同数据链路类型（以太网，3g，LAN）的数据报文统一成相同的形式在网络层中可以互相传播，达到任意具有IP地址的主机。但是数据传输总要经过底层，经过线路传输。这时候就是数据链路层起到了作用，不同链路类型所使用的协议方案都不尽相同，但是在链路层不能使用IP地址了，这时候要找到相对应的主机我就需要MAC地址的作用。

确认网络是否正常以及遇到异常进行异常诊断的协议。其主要功能包括：

主要解决MAC和IP地址之间的问题。确定了IP地址之后可以向对应IP地址的主机发送数据报，但是在底层数据要通过数据链路进行传输，必须知道每个IP地址对应的MAC地址才行。

全局IP要在整个互联网范围内唯一，但是私有地址不需要。NAT就是将私有地址在链接互联网时转换成全局IP是使用的技术。但是实际上nat本质上除了私有地址公有地址转换这一种用处之外最重要的就是将处于内网中的机器进行统一的管理和维护。



# 数据链路层

## 集线器、网桥、交换机、路由器

- 历史—更好理解

  以太网最早出现的时候是一种非常松散的设计思路，当时的网络设计者希望只用一根线，就能让所有连在这根线上的计算机都能够互联。所以最早的以太网是采用同轴电缆，而所有的计算机在这根电缆上通过变压器耦合（可以理解为搭线）在同一根电缆上收发数据。这样就出现了一个问题：一次在这根线上只能有一对收发，否则就会造成干扰。

  所以这样的局域网采用了一种叫做载波侦听/冲突重发的机制：就是如果一个计算机打算向连在这条线上的另一台计算机发送数据，它首先要侦听一下这条线上有没有数据已经在传送，如果没有，就可以发，如果有就再等一段时间后再去侦听一下，直到它可以拿到这根电缆的收发权限。

  这样就造成一个问题：同一时刻只能有一对计算机通信，其他人都要等着。

  假设一个场景，一楼101、102、103和二楼201、202、203连在一根电缆上。假设一楼101和103收发数据很频繁，这样就造成二楼基本没法通信了。怎么办？办法之一就是一楼一根电缆连101、102、103、二楼一根电缆连201、202、203，大家各发各的互不干扰。但是如果，比如201要给102发数据怎么办，这时候就需要一个设备把两根电缆连起来，变成一根电缆。平时一楼和二楼连根电缆是隔离的，只有两个楼层有数据交换才把线连起来，干这个事情的设备就叫网桥。后来交换机出现了，这个问题就不存在了，交换机（理论上）允许任意两个计算机通信互不干扰

- 集线器

  **hub**，以太网设计之初就是想要一个网络接口和多台电脑相连。因此hub就是最简单的连接多台电脑的方式，本质上就是一个信号放大器，这样的话一台电脑发出去的信号就可以被连接到hub上的其他电脑接收到，也就可以通信。一个口发送到的信号原封不动的发送大其他口，只是简单的转发，工作在物理层。

- 网桥

  工作在数据链路层，因此跟其相关的就是mac地址。与hub无差别的转发相比，网桥会过滤mac，只有目的地址mac被匹配了才会发送到出口。（这样可以减少碰撞，冲突）一个网桥就是指的1个输入到1个输出。通俗 说网桥就是把两边设备桥起来，但不是所有流量都放行，而是放行相应mac匹配的。

- 交换机

  随着设备越来越多，如果用网桥来隔离冲突域链接不同网段比较繁琐，因此就出现了交换机。交换机的基本功能与网桥一样，具有帧转发、帧过滤和生成树算法功能。

  但是交换机是多个网桥功能的集合。即网桥一般分有两个端口，而交换机具有高密度的端口。由于交换机能够支持多个端口，因此可以把网络系统划分成为更多的物理网段，这样使得整个网络系统具有更高的带宽。而网桥仅仅支持两个端口，所以，网桥划分的物理网段是相当有限的。

  **网桥和交换机，mac不匹配就flood（泛洪）**，因此泛洪是一种数据链路层的说法。

- 路由器

  路由器工作在网络层，处理IP头部，查路由表，作三层转发。连接在路由器不同端口的设备属于不同的IP子网。

  基于IP地址做转发。

## ping的原理，ping的时候到底发生了什么

- **是什么、有什么用**

  ping在潜水中主要是指收到的声呐脉冲，看看多少米深。在计算机网络中的ping是一个工具，用这个工具来检测网络的连通情况和查看网络的连接速度。

  具体就是用ping命令向想要测试的网络发送测试数据报，以此来查看对方网络是否有响应以及响应速度，达到测试的目的

  ping命令本身使用的的是网络层的ICMP协议，因此ping的本质就是ICMP协议，ICMP又需要通过IP协议进行发送，发送的数据包有一定长度，如果对方网络地址存在并且网络畅通无阻，就会收到同样大小的数据包，当然也有可能超时。因此ping本质就是IMCP协议，通过IP协议发送给对方主机。

  > ping的流程：主机A ping 主机B  ----> 构建ICMP数据包 ----> 构建IP数据包 ----> IP分组 ----> 解析硬件地址封装成帧 ----> 物理层 ---->  网络层传输 ----> 到达主机B ----> 提取IP数据包交给IP层协议 ----> 提取ICMP数据包信息，构建ICMP应答包 ----> 发送给主机A

  >
  >     1. 网络不可达代码为 `0`  —— 当IP地址区分主机号和网络号的时候，由于路由器中的路由表匹配不到对方的网络号
  >     2. 主机不可达代码为 `1`  —— 对端主机没有连接上网络
  >     3. 协议不可达代码为 `2`  —— 当主机以TCP协议访问对端主机的时候，找到对端主机，但是防火墙进制TCP协议访问
  >     4. 端口不可达代码为 `3`  —— 找到对端主机，防火墙也没限制，但是没有进程监听相应端口
  >     5. 需要进行分片但设置了不分片位代码为 `4`  —— 发送端主机发送IP数据包的时候，将IP首部的分片禁止标志位设置为1，由于不进行分片，当途中路由器遇到超过MTU大小的数据包时就直接扔掉，然后报告发送端主机
  >
  >   - 原点抑制消息 —— 类型 `4`
  >
  >     在低速线路中会遇到网络拥堵问题，这个消息就是为了缓和这个拥堵。具体做法是当路由器向低速线路发送数据的时候，其发送队列的缓存变为0而无法发送出去，这个时候路由器向IP源地址即发送端发送一个ICMP原点抑制消息。收到该消息的主机端知道了某个线路发生了拥堵，从而增大IP包的传输间隔，减少网络拥堵。
  >
  >     一般不被使用，因为可能会引起网络不公现象。
  >
  >   - 重定向消息 —— 类型 `5`
  >
  >     如果路由器发送数据报不是从最优路径发送数据的话，会返回一个ICMP重定向消息给发送主机。这个消息中包含了最合适的路由信息和源数据。
  >
  >   - 超时消息 —— 类型 `11`
  >
  >     IP包中有一个叫做TTL(time to live)的东西，他的值每经过一次路由器就会减1，当为0的时候该包就会被丢弃。丢弃的时候路由器就会发送一个ICMP超时消息给发送端主机，通知其该包已经被丢弃了。
  >
  >     设置TTL的目的就是为了防止路由器发送循环状况，避免IP包无休止的在网络上转发。
  >

- **traceroute** 

  traceroute的命令如下：`traceroute 192.168.1.100`

  主要作用有如下：

  1. **故意设置特殊的 TTL，来追踪去往目的地时沿途经过的路由器。**

     原理：它的原理就是利用 IP 包的生存期限 从 1 开始按照顺序递增的同时发送 UDP 包，强制接收 ICMP 超时消息的一种方法。比如，将 TTL 设置 为 1，则遇到第一个路由器，就牺牲了，接着返回 ICMP 差错报文网络包，类型是时间超时。接下来将 TTL 设置为 2，第一个路由器过了，遇到第二个路由器也牺牲了，也同时返回了 ICMP 差错报文数据包，如此往复，直到到达目的主机。这样的过程，traceroute 就可以拿到了所有的路由器 IP。

     > **发送方如何知道发出的 UDP 包是否到达了目的主机呢？**
     >
     > 答：traceroute 在发送 UDP 包时，会填入一个不可能的端口号值作为 UDP 目标端口号（大于 3000 ）。当目的主机，收到 UDP 包后，会返回 ICMP 差错报文消息，但这个差错报文消息的类型是「端口不可达」。所以，当差错报文类型是端口不可达时，说明发送方发出的 UDP 包到达了目的主机。

2.   **故意设置不分片，从而确定路径的 MTU**

   原理：首先在发送端主机发送 IP 数据报时，将 IP 包首部的分片禁止标志位设置为 1。根据这个标志位，途中的路由器不会对大数据包进行分片，而是将包丢弃。随后，通过一个 ICMP 的不可达消息将数据链路上 MTU 的值一起给发送主机，不可达消息的类型为「需要进行分片但设置了不分片位」。发送主机端每次收到 ICMP 差错报文时就减少包的大小，以此来定位一个合适的 MTU 值，以便能到达目标主机。

**CSMA/CD（载波侦听多路访问/冲突检测）**

工作原理：发送数据前 先侦听信道是否空闲 ,若空闲，则立即发送数据。若信道忙碌，则等待一段时间至信道中的信息传输结束后再发送数据；若在上一段信息发送结束后，同时有两个或两个以上的节点都提出发送请求，则判定为冲突。若侦听到冲突,则立即停止发送数据，等待一段随机时间,再重新尝试。总结：先听后发，边发边听，冲突停发，随机延迟后重发。

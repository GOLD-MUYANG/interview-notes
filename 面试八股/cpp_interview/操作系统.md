

# 进程的状态有哪些

操作系统里，**进程的状态**一般分为几个主要的阶段，不同教材或系统叫法稍微不同，但核心一样：

1. **新建（New）**
   - 进程刚被创建，还没被操作系统调度运行。
2. **就绪（Ready）**
   - 进程已分配好资源（除了CPU），随时可以运行，等待CPU调度。
3. **运行（Running）**
   - 进程正在CPU上执行。
   - 在单核CPU上，同一时刻只有一个进程处于运行态。
4. **阻塞 / 等待（Blocked / Waiting）**
   - 进程因为等待某些事件（比如磁盘I/O、网络、用户输入）而暂停，暂时不能运行。
5. **结束（Terminated）**
   - 进程执行完毕，或被系统/用户终止，进入结束状态，等待回收资源。

# 进程和线程的区别和联系

## 一、概念层面

- **进程（Process）**
  - 系统中正在运行的程序。
  - 是**资源分配的基本单位**（内存、文件、I/O 设备）。
  - 每个进程有独立的地址空间，互相隔离。
  - Windows 任务管理器中的一行就是一个进程。
- **线程（Thread）**
  - 是**CPU 调度的基本单位**。
  - 同一进程下的多个线程共享进程资源（代码段、全局变量、文件句柄），但各自有**独立的栈和寄存器**。
  - 线程创建开销比进程小，通信比进程间容易。

> 类比：进程 = 火车，线程 = 车厢。
>
> - 火车（进程）可以有多个车厢（线程）。
> - 不同火车的乘客很难互换（进程间通信复杂）。
> - 同一列火车的乘客换车厢很容易（线程间共享数据简单）。

------

## 二、内核实现层面（Linux）

- 内核中进程和线程没有本质区别，都用 **task_struct** 结构体表示，统称为 **task**。
- 区别在于创建时使用的 **clone() 参数**不同：
  - **进程**：fork() → do_fork(SIGCHLD) → 独立的内存、文件表。
  - **线程**：pthread_create() → clone(CLONE_VM | CLONE_FS | CLONE_FILES …) → 与父进程共享内存、文件表。
- **标识**
  - 每个 task 都有一个唯一的 **pid**。
  - 对于线程，还会有一个 **tgid**（所属进程 ID）。
  - 所以一个进程下的多个线程有不同 pid，但 tgid 相同。

------

## 三、性能差异

- 进程上下文切换：**2.7 ~ 5.5 μs**
- 线程上下文切换：**约 3.8 μs**
- 差距并不大，但线程更适合频繁交互和共享数据的场景。

------

## 四、对比总结

| 对比项   | 进程                                               | 线程                                     |
| -------- | -------------------------------------------------- | ---------------------------------------- |
| 定义     | 资源分配的单位                                     | 调度的单位                               |
| 内存空间 | 独立                                               | 共享（代码/全局变量），私有（栈/寄存器） |
| 开销     | 创建/切换开销大                                    | 开销小                                   |
| 通信     | 进程间通信复杂（管道、消息队列、共享内存、socket） | 线程间通信简单（共享变量 + 同步机制）    |
| 稳定性   | 一个进程崩溃不影响其他进程                         | 一个线程崩溃会影响整个进程               |
| 本质     | 内核中的一个 task_struct                           | 也是 task_struct，只是带 CLONE 标志      |

**比喻**

做个简单的比喻：进程=火车，线程=车厢

1. 线程在进程下行进（单纯的车厢无法运行）
2. 一个进程可以包含多个线程（一辆火车可以有多个车厢）
3. 不同进程间数据很难共享（一辆火车上的乘客很难换到另外一辆火车，比如站点换乘）
4. 同一进程下不同线程间数据很易共享（A车厢换到B车厢很容易）
5. 进程要比线程消耗更多的计算机资源（采用多列火车相比多个车厢更耗资源）
6. 进程间不会相互影响，一个线程挂掉将导致整个进程挂掉（不一定）（一列火车不会影响到另外一列火车，但是如果一列火车上中间的一节车厢着火了，将影响到所有车厢）
7. 线程使用的内存地址可以上锁，即一个线程使用某些共享内存时，其他线程必须等它结束，才能使用这一块内存。（比如火车上的洗手间）－"互斥锁"



# 线程调度为什么比进程调度更少开销？ 

关键点在于 **上下文切换（context switch）**。

当 CPU 从一个任务切换到另一个任务时，需要保存当前任务的状态，再恢复另一个任务的状态。这个过程就叫上下文切换。

------

### 进程调度开销大

- 切换进程时，需要切换 **独立的地址空间**：
  - 内核要保存和恢复 **页表**（虚拟内存到物理内存的映射）。
  - 刷新 TLB（Translation Lookaside Buffer，CPU 的地址缓存），否则可能访问到旧进程的地址。
  - 需要切换文件描述符表、信号处理表等资源。

这些操作都涉及内核态复杂的数据结构，成本较高。

------

### 线程调度开销小

- 线程属于同一进程，共享 **地址空间和资源**。
- 切换线程时：
  - 只需要保存/恢复 **CPU 寄存器、程序计数器、栈指针** 等线程私有的数据。
  - 不需要切换页表、刷新 TLB，因为它们都在同一进程空间里。

所以，线程调度比进程调度少了很多“系统资源切换”的步骤。

------

### 总结表

| 项目     | 进程调度                                           | 线程调度                      |
| -------- | -------------------------------------------------- | ----------------------------- |
| 切换内容 | CPU寄存器、程序计数器、内核栈、页表、TLB、文件表等 | CPU寄存器、程序计数器、线程栈 |
| 地址空间 | 要切换                                             | 不切换（共享）                |
| 开销     | 大                                                 | 小                            |





# 线程和进程之前共享那些资源？

### 1. 共享的

同一进程中的多个线程会共享以下资源：

- **代码段（Text Segment）**：程序指令。
- **全局变量、静态变量（Data Segment）**。
- **堆（Heap）**：动态分配的内存（malloc/new）。
- **文件描述符表（File Descriptors）**：打开的文件、socket。
- **信号处理方式**。
- **当前工作目录、进程环境变量**。
- **地址空间（虚拟内存页表）**。

👉 这些共享资源保证了线程之间能很方便地通信和协作。

------

### 2. 独有的

每个线程也有自己的私有数据，用来维持独立运行：

- **线程栈（Stack）**：存放局部变量、函数调用信息。
- **寄存器上下文（Program Counter, SP 等）**。
- **线程 ID（TID，Linux 下其实就是一个 pid）**。
- **信号屏蔽字**（mask）。

👉 这些是线程切换时需要保存和恢复的核心内容。



# 进程同步

## 一、进程同步到底在解决什么问题

多个进程并发执行时，会出现两种问题：

- **互斥问题**：多个进程同时访问共享资源，可能造成数据错误。
- **同步问题**：多个进程需要按照一定顺序协作执行。

因为有问题，所以就要解决问题，怎么解决这两种问题，就是在讲进程同步。

进程同步研究的是：

> 多个进程并发运行时，如何控制它们访问共享资源的方式和执行先后顺序，避免程序出错。

## 二、第一类制约：共享资源产生的互斥关系

### 临界资源

一次只允许一个进程使用的共享资源，称为**临界资源**。它是互斥保护的对象

因为临界资源一次只能由一个进程使用，所以操作系统必须控制进程的执行顺序：

```
进程 A 使用临界资源时
        ↓
进程 B 必须等待
        ↓
进程 A 使用完并释放资源
        ↓
进程 B 才能继续使用
```

因此，临界资源产生了进程之间的互斥制约关系。

### 临界区

临界资源是资源，临界区是代码。

进程中访问临界资源的那段代码，称为**临界区**。

#### 临界区管理需要满足什么要求

1. **空闲让进**：当临界区空闲时，应允许一个请求进入的进程立即进入。
2. **忙则等待**：当已有进程进入临界区时，其他进程必须等待。
3. **有限等待**：保证请求进入临界区的进程在有限时间内能进入，防止“饿死”。
4. **让权等待**：若进程不能进入临界区，应立即释放 CPU，避免忙等浪费资源。



## 三、第二类制约：进程协作产生的同步关系

有些进程即使没有同时争抢资源，也必须按照一定顺序执行。

例如生产者和消费者：

```
生产者生成数据
        ↓
生产者将数据放入缓冲区
        ↓
消费者才能取出数据
```

同步关系关注的是：

> 某个条件没有满足时，进程必须等待；条件满足以后，进程才能继续执行。



## 如何实现互斥和同步

确定进程之间存在互斥或同步关系之后，还需要具体机制来控制进程执行。

常见机制包括：

- 关闭中断；因为时钟中断被关闭，当前执行过程不会被其他进程打断。
- 自旋锁；一直占用 CPU，等待进程会不断检查锁是否释放，释放后再执行那些进程的操作
- 互斥锁；
- 信号量；
- 条件变量；
- 读写锁。

其中，信号量既可以实现互斥，也可以实现同步。

------

## 经典同步问题

1. **生产者–消费者问题**
   - **核心**：生产者放数据，消费者取数据。
   - **难点**：避免“缓冲区溢出”和“缓冲区空取”。
2. **哲学家进餐问题**
   - **核心**：哲学家围坐一桌，筷子数量有限，如何避免死锁与饥饿。
3. **读者–写者问题**
   - **核心**：多个读者可以并发读，但写者必须独占。
   - **难点**：平衡读写，避免读者或写者长期得不到执行。

------

✅ **总结一句话**：
 进程同步的目标是 **保证共享资源互斥访问**，同时 **维持进程协作顺序**；常见机制有 **中断屏蔽、自旋锁、信号量**；典型案例是 **生产者-消费者、哲学家进餐、读者-写者**。



# CPU 调度算法

## 1. 什么是 CPU 调度

多个进程可能同时处于**就绪状态**，但一个 CPU 核心同一时刻只能运行一个进程。

因此，操作系统需要决定：

> 接下来把 CPU 分配给哪个就绪进程。

这个过程称为**进程调度**或 **CPU 调度**。

------

## 2. 抢占式与非抢占式

### 非抢占式调度

进程获得 CPU 后，会一直运行，直到：

- 运行结束；
- 主动阻塞，例如等待磁盘或网络数据。

操作系统不会强行中断它。

### 抢占式调度

进程正在运行时，操作系统可以暂停它，把 CPU 分配给其他进程。

常见抢占原因：

- 时间片用完；
- 更高优先级的进程进入就绪队列；
- 当前进程已经运行较长时间。

------

## 3. 常见调度算法

### 3.1 先来先服务 FCFS

按照进程进入就绪队列的先后顺序调度：

> 谁先来，谁先运行。

进程获得 CPU 后，会一直运行到结束或阻塞，因此通常属于**非抢占式调度**。

**优点：**

- 实现简单；
- 调度顺序明确。

**缺点：**

- 如果前面是一个长任务，后面的短任务需要等待很久；
- 容易出现“短任务被长任务拖住”的情况。

------

### 3.2 最短作业优先 SJF

优先运行预计执行时间最短的进程。

例如：

```text
进程 A：预计运行 10 秒
进程 B：预计运行 2 秒
进程 C：预计运行 1 秒
```

调度顺序通常为：

```text
C → B → A
```

**优点：**

- 可以减少平均等待时间；
- 有利于快速完成大量短任务。

**缺点：**

- 很难准确知道进程还需要运行多久；
- 长任务可能一直被短任务插队，出现饥饿。

------

### 3.3 高响应比优先 HRRN

高响应比优先用于平衡“等待时间”和“运行时间”。

计算公式：

```text
响应比 =（等待时间 + 服务时间）/ 服务时间
       = 1 + 等待时间 / 服务时间
```

每次调度时，选择响应比最高的进程。

它具有两个特点：

- 短任务的服务时间小，响应比较高；
- 长任务等待得越久，响应比也会不断提高。

因此，它既照顾短任务，也能降低长任务长期得不到运行的概率。

通常属于**非抢占式调度**。

------

### 3.4 时间片轮转 RR

操作系统给每个进程分配一小段运行时间，称为**时间片**。

例如时间片为 20ms：

```text
A 运行 20ms → B 运行 20ms → C 运行 20ms → A 再运行
```

如果进程在时间片内没有执行完成，就会被暂停并放回就绪队列末尾。

如果进程提前结束或阻塞，CPU 会立即调度下一个进程。

**优点：**

- 每个进程都能较快获得 CPU；
- 响应速度较好；
- 适合分时系统和交互式任务。

**缺点：**

- 时间片太大，会接近 FCFS；
- 时间片太小，会频繁切换进程，增加上下文切换开销。

时间片轮转属于**抢占式调度**。

------

### 3.5 优先级调度

为每个进程设置优先级，优先运行优先级更高的进程。

它可以分为两种。

#### 非抢占式优先级调度

即使有更高优先级的进程到来，也要等当前进程结束或阻塞后，才能调度它。

#### 抢占式优先级调度

如果更高优先级的进程进入就绪队列，操作系统会立即暂停当前进程，运行高优先级进程。

**主要问题：**

低优先级进程可能长期得不到运行，出现饥饿。

常见解决方法是**老化机制**：

> 进程等待时间越长，逐渐提高它的优先级。

------

### 3.6 多级反馈队列 MLFQ

多级反馈队列结合了：

- 优先级调度；
- 时间片轮转；
- 抢占式调度。

系统设置多个就绪队列：

```text
第 1 级队列：优先级最高，时间片最短
第 2 级队列：优先级较低，时间片较长
第 3 级队列：优先级更低，时间片更长
```

基本运行规则：

1. 新进程首先进入最高优先级队列。
2. 同一队列中的进程按照时间片轮转运行。
3. 如果进程用完时间片仍未结束，就下降到下一级队列。
4. 只有高优先级队列为空，才会运行低优先级队列。
5. 如果高优先级队列出现新进程，可以抢占当前低优先级进程。

这样会产生一种效果：

- 运行时间短、经常阻塞的交互式任务，大多停留在高优先级队列；
- 长时间占用 CPU 的任务，会逐渐下降到低优先级队列。

因此，多级反馈队列不需要提前知道任务运行时间，也能兼顾响应速度和整体效率。

------

## 4. 简单对比

| 算法         | 核心规则                       | 是否抢占 | 主要问题             |
| ------------ | ------------------------------ | -------- | -------------------- |
| FCFS         | 谁先来谁先运行                 | 否       | 长任务拖住短任务     |
| SJF          | 最短任务先运行                 | 通常否   | 长任务可能饥饿       |
| HRRN         | 响应比最高的先运行             | 通常否   | 需要估算服务时间     |
| RR           | 每个进程轮流运行一个时间片     | 是       | 时间片大小难选择     |
| 优先级调度   | 优先级高的先运行               | 两者都可 | 低优先级进程可能饥饿 |
| 多级反馈队列 | 高优先级短时间片，未完成则降级 | 是       | 实现和参数设置较复杂 |



# 操作系统是如何做到进程阻塞的？

操作系统实现**进程阻塞**主要靠**调度和状态管理**，原理如下：

------

## 1. **进程状态**

操作系统对每个进程维护一个**状态机**，主要状态有：

- **就绪（Ready）**：可以运行，等待 CPU 分配。
- **运行（Running）**：正在 CPU 上执行。
- **阻塞（Blocked/Waiting）**：无法继续运行，需要等待某个事件（I/O 完成、资源可用、信号到达）。

阻塞就是**把进程从“运行/就绪”状态切换到“阻塞状态”**，直到条件满足才恢复就绪。

------

## 2. **阻塞的触发条件**

- **I/O 等待**：进程请求磁盘、打印机等设备，操作系统将其阻塞，等设备准备好再唤醒。
- **等待资源**：进程请求锁、信号量或共享资源，如果不可用，就阻塞。
- **同步事件**：等待其他进程的信号或条件变量。

------

## 3. **阻塞实现机制**

1. **进程控制块（PCB）更新**
   - 内核在 PCB 里修改状态字段为“阻塞”，并记录阻塞原因。
2. **调度器介入**
   - 阻塞的进程从就绪队列移除，不再分配 CPU。
   - CPU 分配给其他就绪进程。
3. **唤醒条件满足**
   - 例如 I/O 完成或信号到达，内核将进程状态改回就绪。
   - 下次调度时就可能获得 CPU。

------

## 4. **小结**

- 阻塞**不消耗 CPU**，只是在等待事件。
- 核心依赖：**进程状态管理 + 调度器 + 内核事件通知机制**。





# 进程和线程的通信方式

## 进程

首先进程与进程之间是互相看不见的，每个进程都有独立的虚拟地址空间，不是同一块物理内存。那么这里就要解决的是怎么从一块儿内存把信息转移到另一块儿内存

### 进程间通信：先解决“数据看不见”

#### 第一类：操作系统帮忙转交数据

包括：

- 管道
- 消息队列
- Socket

数据流向是：

```
进程 A
   ↓ 写入
内核缓冲区
   ↓ 读取
进程 B
```

数据通常需要：

1. 从进程 A 的用户空间复制到内核；
2. 再从内核复制到进程 B 的用户空间。

#### 第二类：让两个进程直接看到同一块内存

包括：

- 共享内存
- `mmap`

数据流向不再是“写内核，再由对方读取”，而是：

```
进程 A 虚拟地址 ─┐
                  ├─ 同一块物理内存
进程 B 虚拟地址 ─┘
```

进程 A 写入以后，进程 B 可以直接读取。



#### 第三类：只发送通知，不传大量数据

信号

例如：

- `SIGINT`：用户按下 Ctrl+C；
- `SIGTERM`：请求进程终止；
- `SIGCHLD`：子进程状态发生变化；
- `SIGSEGV`：非法内存访问。



## 线程

可以认为在同一段代码里面开了两个线程，两个线程都要访问某个变量，而他们都在这个程序里，所以都能拿到，因此线程间不太需要专门的数据传输机制，反而是需要手段来控制不要瞎读写。

那么就需要

- 锁
- 条件变量
- 信号量





# 线程是如何实现的？

线程主要有三种实现模型：

1. **1:1 内核线程模型**：每个用户线程对应一个内核线程，由操作系统直接调度。它可以利用多核，一个线程阻塞不会影响其他线程，但线程创建和切换成本较高。

   Linux、Windows 中常用的普通线程，基本都是这种 **1:1 模型**。

   例如：

   ```
   std::thread
   pthread_create
   ```

   它们是用户层提供的接口，但创建出来的线程最终会被内核直接调度。

   

2. **N:1 用户线程模型**：多个用户线程运行在一个内核线程上（内核视角：这个进程只有一个线程。实际上有仨，但是内核不知道），用户线程库自己创建线程，保存状态，上下文切换。（和协程差不多）。但是这样一个线程阻塞，可能导致所有线程一起阻塞，然后三个用户线程最终都运行在同一个内核线程上，不算真正的并发。



1. **M:N 混合模型**：多个用户线程映射到多个内核线程，由用户态运行时和操作系统共同调度。它兼顾大量轻量线程和多核并行，但调度实现比较复杂。

用户线程 A ─┐
用户线程 B ─┼── 内核线程 1
用户线程 C ─┤
用户线程 D ─┼── 内核线程 2
用户线程 E ─┘



# 线程调度

线程调度是操作系统或运行时系统决定**哪个线程什么时候执行**的机制。主要有两种方式：

------

## 1. **协同式调度（Cooperative Scheduling）**

- **原理**：线程自己决定何时让出 CPU，执行完自己的工作后主动通知系统切换线程。
- **优点**：
  - 实现简单。
  - 不易出现线程同步问题（因为线程按顺序运行）。
- **缺点**：
  - 线程执行时间不可控制。
  - 如果某个线程一直不让出 CPU，整个程序可能被阻塞。
- **应用**：早期系统或某些嵌入式系统。

------

## 2. **抢占式调度（Preemptive Scheduling）**

- **原理**：系统分配线程的执行时间，线程切换由系统控制，而不是线程自己决定。
- **优点**：
  - 系统可控线程执行时间。
  - 单个线程问题不会导致整个进程阻塞。
- **应用**：现代操作系统、多线程语言（如 Java）。





# 进程、线程、协程的区别

```
进程：资源分配单位
线程：CPU 调度单位
协程：用户态调度的执行单元
```

三者不是同一层级：

```
一个进程
 ├─ 一个或多个线程
 │   ├─ 一个或多个协程
 │   └─ 一个或多个协程
 └─ 共享进程资源
```

## 协程和线程最关键的区别

### 线程由内核调度

线程什么时候暂停，什么时候运行，主要由操作系统决定。

```
操作系统：
线程 A 时间片到了，暂停
线程 B 开始运行
```

这是抢占式调度。

### 协程由用户程序调度

协程一般在自己执行到等待点时主动让出：

```
协程 A：
我要等网络数据，先让别人运行
```

调度器再运行协程 B。

这是协作式调度。

## 协程为什么轻量

创建一个线程，通常需要：

- 进入内核
- 创建内核调度对象
- 分配线程栈
- 设置调度信息

线程栈通常比较大，可能是几 MB。

协程通常只需要：

- 保存少量寄存器
- 保存执行位置
- 保存局部变量
- 分配较小的栈，或者根本没有独立栈

因此可以创建很多协程：

```
几万个协程
```

但一般不能随便创建几万个操作系统线程。

# 不可中断的阻塞态怎么看到呢？什么原因造成不可中断的阻塞态进程

## 定义

**不可中断阻塞态（Uninterruptible Sleep，STAT = D）**

是指进程在内核态执行时，**因为等待某个硬件资源或内核操作完成而进入的阻塞状态**。

在这个状态下，进程**不能被信号打断**（比如 `kill -9` 也没法杀掉），只有等等待的事件完成了，才会继续执行。

------

## 1. 怎么看到不可中断阻塞态进程

在 **Linux** 系统里：

- 执行 `ps -aux` 或 `top`，会在 **STAT** 栏看到进程状态。
- 常见标记：
  - `R` → 运行
  - `S` → 可中断睡眠（Sleep）
  - `D` → **不可中断睡眠（Uninterruptible Sleep）**
  - `Z` → 僵尸

所以，**STAT = D** 的进程就是不可中断阻塞态。

------

## 2. 什么原因会造成不可中断阻塞态

不可中断的阻塞，一般是因为进程正在等待某些**不能被打断的内核操作**，主要包括：

### 等待磁盘 I/O

比如进程在读写磁盘时，内核必须等硬件完成，不能被中断信号打断。

### 等待网络 I/O（驱动层面）

内核等待网卡/驱动完成数据传输时。

### 等待设备响应（比如 USB、SCSI 设备）

某些驱动操作必须完成才能返回，进程只能卡在那里。

### 锁等待（内核中的一些锁不可中断）

比如持有内核态的 **mutex/semaphore** 时，另一个进程阻塞等待。

------

## 3. 为什么要设计不可中断的阻塞

- 有些操作必须“要么成功，要么死等”，不能中途退出，否则会破坏内核和硬件的数据一致性。
- 举例：进程正在写磁盘，如果强行打断，文件系统可能就坏了。

常见原因包括：

1. 磁盘或块设备 I/O 卡住；
2. NFS 等远程文件系统无响应；
3. 设备或驱动异常；
4. 文件系统回写、内存回收阻塞；
5. 内核锁长时间未释放。

因为阻塞了得不到cpu，怎么占用CPU资源





# 僵尸进程什么原因，僵尸进程占有什么资源呢

## 1. **僵尸进程的原因**

- 当一个进程调用 `exit()` 结束时，内核会：
  1. 回收它占用的 **大部分资源**（内存、文件描述符、CPU调度信息等）。
  2. 但是会留下一个很小的记录（进程号 PID、退出状态、运行时间等），存放在 **进程表** 中。
- 这样父进程可以通过 `wait()` 或 `waitpid()` 系统调用读取子进程的退出状态。
- 如果父进程 **没有调用 wait() 读取子进程信息**，子进程的这一点残留信息就一直留在内核 → 形成 **僵尸进程 (Zombie Process)**。

------

## 2. **僵尸进程占用的资源**

- 已经释放：
  - 内存（代码段、堆、栈）
  - 打开的文件描述符
  - 其他所有运行资源
- 还占用：
  - **进程表中的一条记录**（包含 PID、退出码、一些统计信息）
  - 也就是说，僵尸进程几乎不占内存，只占 **一个 PID 和内核表项**。

------

## 3. **为什么僵尸进程有害**

- 单个僵尸进程资源消耗很小，不会影响系统。
- 但如果父进程长期不处理子进程，僵尸进程会越来越多，**占满进程表**（系统能同时存在的 PID 数是有限的，Linux 默认 32768 或更多）。
- 一旦进程表满了，就无法再创建新进程，系统就会出大问题。



# linux内核的同步方式

首先要明确，同步和互斥是计算机系统中，用于控制进程对某些特定资源访问的机制。同步指的是进程按照一定的顺序和规则访问资源，互斥则是控制资源某一时刻只能由一个进程访问。这样看来互斥是同步的一种情况。

在现代操作系统里，同一时间可能有多个内核执行流在执行，因此内核其实象多进程多线程编程一样也需要一些同步机制来同步各执行单元对共享数据的访问。尤其是在多处理器系统上，更需要一些同步机制来同步不同处理器上的执行单元对共享的数据的访问。在主流的Linux内核中包含了几乎所有现代的操作系统具有的同步机制，**这些同步机制包括：原子操作、信号量（semaphore）、读写信号量 （rw_semaphore）、spinlock、BKL(Big Kernel Lock)、rwlock、brlock（只包含在2.4内核中）、RCU（只包含在2.6内核中）和seqlock（只包含在2.6内核中）。**

> linux会因为三种机制而产生并发，需要进行同步。
>
> 1. **中断。**中断就是操作系统随时可以打断正在执行的代码。当进程访问某个临界资源发生中断，会进入中断处理程序。中断处理程序也可能访问该临界资源。
> 2. **内核抢占式调度。**内核中正在执行的任务被另外一个任务抢占。
> 3. **多处理器并发。**每个处理器都可以调度一个进程，多个进程可能会造成并发。

- **禁用中断**

  对于单处理器不可抢占系统来说，系统并发源主要是中断处理。因此在进行临界资源访问时，进行禁用/使能中断即可以达到消除异步并发源的目的。

- **原子操作**

  原子操作保证指令在运行时候不会被任何事物或者事件打断，把读和写的行为包含在一步中执行，避免竞争。

- **内存屏障(memory barrier)**

  程序在运行时内存实际的访问顺序和程序代码编写的访问顺序不一定一致，这就是内存乱序访问。内存乱序访问行为出现的理由是为了提升程序运行时的性能。内存乱序访问主要发生在两个阶段：

  1. 编译时，编译器优化导致内存乱序访问（指令重排）
  2. 运行时，多 CPU 间交互引起内存乱序访问

- **自旋锁(spin lock)**

  对于复杂的操作原子操作是不能的。比如从一种数据结构中读取数据，写入到另一种数据结构中。自旋锁是linux内核中最常见的一种锁。自旋锁只能被一个可执行线程所拥有，如果有线程要抢占一个已经被占有的自旋锁，则其会一直进行循环来等待锁重新可用。当锁被释放后，请求锁的执行线程便能立刻得到它。其实就是忙等自旋锁只适用于那些在临界区停留很短时间的加锁操作。因为线程在等待锁期间会一直占据处理器，如果长时间等待锁会导致处理器效率降低。而如果线程占用锁只需要短暂的执行一下，那么使用自旋锁更优，因为不需要进行上下文的切换。

- **信号量**

  可以理解为一种“睡眠锁”

  自旋锁是“忙等”机制，在临界资源被锁定的时间很短的情况下很有效。但是在临界资源被持有时间很长或者不确定的情况下，忙等机制则会浪费很多宝贵的处理器时间。

  而信号量机制在进程无法获取到临界资源的情况下，立即释放处理器的使用权，并睡眠在所访问的临界资源上对应的等待队列上；在临界资源被释放时，再唤醒阻塞在该临界资源上的进程。信号量适用于长时间占用锁的情形。

- **读-写自旋锁**

  具体就是在读写场景中了，为读和写提供不同的锁机制。

  当一个或者多个读任务时可以并发的持有读锁，但是写锁只能被一个人物所持有的。即对写者共享对读者排斥

- **读写信号量**

  这个和读写自旋锁的思想是一样的。

- **mutex体制**

  也是一种睡眠锁，是实现互斥的特定睡眠锁。是一种互斥信号

  使用mutex有很多限制，不像信号量那样想用就用

  1. 任何时刻只有一个任务可以持有mutex，引用计数只能是1
  2. 给mutex上锁必须给其解锁，严格点就是必须在同一上下文中上锁和解锁
  3. 持有mutex的进程不能退出
  4. 等等

- **完成变量(completion variable)**

  内核中一个任务需要发出信号通知另一个任务发生了某个特定事件，利用完成变量使得两个任务实现同步

- **BLK：大内核锁**

  属于混沌时期的产物，是一个全局的自旋锁

  这个东西是早期linux不支持线程的时候用的，和自旋锁差不多的思想。

  现在一般不鼓励使用这个了

- **顺序锁**

  这种锁用于读写共享数据。

  实现这个机制主要依靠序列计数器，当写数据时，会得到一个锁，序列值会增加。在读取数据前后这两个时间内，序列值都会被读取

  如果读取的序列号值相同，表明读操作在进行的过程中没有被写操作打断，

- **关闭内核抢占**

  内核是抢占性的，因此内核中的进程在任何时候都可能停下来以便让另一个具有更高优先级的进程运行。但是一个任务和被抢占的任务可能在同一个临界区运行。为了避免上述情况，当使用自旋锁时这个区域被标记为非抢占的，一个自旋锁被持有表示内核不能抢占调度。

  但是在一些情况下，就算不用自旋锁，也要关闭内核抢占。

  比如，对于只有一个处理器能够访问到数据，原理上是没有必要加自旋锁的，因为在任何时刻数据的访问者永远只有一位。但是，如果内核抢占没有关闭，则可能一个新调度的任务就可能访问同一个变量。
  
  所以这时候害怕的不是多个任务访问同问同一个变量，而是一个任务的访问还没有完成就转到了另一个任务。
  
- **RCU(Read, Copy, Update)**

  RCU(Read, Copy, Update)是一组Linux内核API，实现了一种同步机制，允许多个读者与写者并发操作而不需要任何锁，这种同步机制可以用于保护通过指针进行访问的数据。比较适合用在读操作很多而写操作极少的情况，可以用来替代读写锁。

  一个典型场景就是内核路由表，路由表的更新是由外部触发的，外部环境的延迟远比内核更新延迟高，在内核更新路由表前实际已经向旧路径转发了很多数据包，RCU读者按照旧路径再多转发几个数据包是完全可以接受的，而且由于RCU的无锁特性，实际上相比有锁的同步机制，内核可以更早生效新的路由表。路由表这个场景，以系统内部短时间的不一致为代价，降低了系统内部与外部世界的不一致时间，同时降低了读者成本。

  > Q: **为什么只能保护通过指针访问的数据？**
  >
  > A: 任何CPU架构下的Linux都可以保证指针操作的原子性，这是无锁并发的前提。也就是说，假设CPU A在修改指针，无论何时CPU B读取该指针，都可以保证读取到的数据要么是旧的值，要么是新的值，绝不会是混合新旧值不同bit位的无意义值。因此使用RCU对更复杂的数据结构的保护都是基于对指向该数据结构的指针的保护。



# 死锁

**概念**：

- 在并发环境中，多个进程因争夺资源而互相等待，形成**永远无法继续执行的状态**。
- 死锁会浪费系统资源，降低 CPU 吞吐量和计算机性能。

------

## 1. **死锁产生的原因**

1. **资源分配不当**
2. **进程运行顺序不合理**

------

## 2. **死锁产生的必要条件（四个必要条件）**

> 当以下四个条件同时成立时，必然会发生死锁：

1. **互斥（Mutual Exclusion）**
   - 某个资源一次只能被一个进程使用。
2. **占有且等待（Hold and Wait）**
   - 进程已占有一些资源，同时还在等待其他资源。
3. **不可抢占（No Preemption）**
   - 已被占有的资源不能被强行抢走，必须等进程释放。
4. **循环等待（Circular Wait）**
   - 存在一个进程循环链，每个进程等待下一个进程持有的资源。

------

## 3. **避免死锁的方法**

核心思路：破坏“占有且等待”、“不可抢占”或“循环等待”条件（互斥条件必须保留）。

### (1) 破坏“占有且等待条件”

- 方法：
  1. 所有进程在开始运行前，一次性申请所需的全部资源。
  2. 进程使用完资源后释放，然后再申请新的资源。

### (2) 破坏“不可抢占条件”

- 方法：当进程请求不到所需资源时，必须释放已占有的资源。

### (3) 破坏“循环等待条件”

- 方法：对资源进行**有序编号**，所有进程申请资源必须按照固定顺序执行。

### (4) 银行家算法（Banker’s Algorithm）

- **原理**：系统在分配资源前判断分配后是否处于**安全状态**：
  - 安全状态 → 系统能避免死锁
  - 不安全状态 → 可能进入死锁，但不一定死锁
- **执行条件**：进程必须预先声明最大资源需求，系统资源总量固定。
- **流程**：
  1. 当进程提出资源请求，系统判断是否安全。
  2. 安全 → 分配资源。
  3. 不安全 → 不分配，进程阻塞等待。

------

✅ **总结**

- 死锁是并发系统中不可忽视的问题。
- 避免死锁的关键是**打破四个必要条件中的至少一个**。
- 银行家算法是动态安全检测的一种方法，可防止死锁发生。



# 虚拟内存相关知识点

从下面几个点进行叙述

```
直接使用物理内存有什么问题 → 引入虚拟地址 → 内存不够怎么办 → 按页装入 → 怎么找到物理地址 → 页面不在内存怎么办 → 页表太慢、太大怎么办。
```

## 一、虚拟内存到底是什么

先记住一句话：

> **程序使用的是虚拟地址，真正的数据存放在物理内存中，操作系统和硬件负责把两者对应起来。**

程序执行：

```
int a = 10;
```

程序只知道变量 `a` 位于某个地址，例如：

```
虚拟地址 0x1000
```

但数据真正可能放在：

```
物理内存地址 0x8000
```

这个转换过程对程序基本是透明的。



## 二、为什么需要虚拟内存

虚拟内存主要解决三个问题。

### 问题一：多个程序会互相破坏内存

多个程序同时修改同一块儿地址造成混乱，而且还可能发生普通程序修改操作系统所在的内存的情况。不能让所有程序直接随意访问物理内存。程序统一用虚拟内存隔开，就是加了一层中间层，现在可以做更多控制了

用虚拟内存解决进程之间的内存隔离问题。

### 问题二：程序不应该关心物理内存位置

程序要想运行，得知道

```
代码放在哪里 数据放在哪里 堆放在哪里 栈放在哪里
```

但程序每次运行时，空闲的物理内存位置可能都不同。

用虚拟内存，程序统一使用自己的虚拟地址，程序始终认为自己从某个固定的虚拟地址开始运行，操作系统再负责把这些虚拟地址映射到当前可用的物理内存。

### 问题三：程序需要的内存可能超过物理内存

一个程序可能很大，比物理内存的真实大小还大，但是程序在执行的时候不必同时使用全部代码和数据，那就分开加载，把当前需要的部分放进物理内存。



## 三、虚拟内存是怎么工作的

虚拟内存不会把程序看成一个完整的大块，而是把内存切成许多固定大小的小块。

虚拟地址空间中的块叫：

> **页，Page**

物理内存中的块叫：

> **页框（物理块），Page Frame**

页和页框大小相同，常见大小是：

```
4KB
```

虚拟页不要求按照顺序存放在物理内存中。

例如：

```
虚拟页 0 → 物理页框 5
虚拟页 1 → 物理页框 2
虚拟页 2 → 暂时不在内存
虚拟页 3 → 物理页框 7
```

这就是分页。

## 四、虚拟地址怎么转换成物理地址

一个虚拟地址可以分成两部分：

```
虚拟地址 = 虚拟页号 + 页内偏移量
```

假设一页大小是 4KB，即 4096 字节。

虚拟地址 `8196` 可以拆成：

```
8196 = 2 × 4096 + 4
```

```
虚拟地址 8196
↓ 拆分 
虚拟页号 2 + 页内偏移量 4
↓ 查询页表
虚拟页 2 对应物理页框 6
↓ 
物理地址 = 6 × 4096 + 4
```

页内偏移量不会改变，只需要把虚拟页号替换成物理页框号。



## 五、页表是什么

页表可以理解成一张映射表。

它记录：

```
某个虚拟页 → 某个物理页框
```

例如：

| 虚拟页 | 物理页框 |
| ------ | -------- |
| 0      | 5        |
| 1      | 2        |
| 2      | 不在内存 |
| 3      | 7        |

每个进程都有自己的页表。

所以，即使两个进程使用相同的虚拟地址，它们也可以得到不同的物理地址。





## 六、MMU 和TLB 是什么

### MMU ：

**MMU是内存管理单元，Memory Management Unit**

至于为什么需要这个东西

> **页表只是记录映射关系的数据表。**只是一堆存放在内存中的数据，它自己不会运行，也不会主动转换地址。
>  **MMU 才是读取页表、执行地址转换的硬件。**

CPU每执行一次读写内存，产生的通常都是虚拟地址。数量一大速度就慢了。页表算是一个软件，和硬件比起来还是太慢了，所以专门设计的MMU



### TLB

看页表还是太慢了，就想着能不能直接找最近访问过的映射关系，毕竟最近访问过的可能还会被访问。

那MMU 内部还有一个高速缓存，叫 **TLB**：

TLB，存储最近使用过的映射缓存





## 七、操作系统对虚拟内存有什么用

正常转换时，操作系统一般不参与：

```
CPU → MMU → TLB/页表 → 物理内存
```

只有出现异常情况，例如页表中没有有效映射时：

```
MMU 查询页表
        ↓
发现页面不存在或没有权限
        ↓
触发缺页异常
        ↓
操作系统开始处理
```

### 处理过程（简单记一下就行，这是缺页中断处理过程。）

```
程序访问某个虚拟地址
        ↓
页面是否在物理内存？
        ├── 是 → 正常访问
        │
        └── 否 → 触发缺页异常
                    ↓
              地址是否合法？
                ├── 否 → 终止进程
                │
                └── 是
                    ↓
              是否有空闲页框？
                ├── 是 → 直接使用
                │
                └── 否
                    ↓
              执行页面置换算法
                    ↓
              被淘汰页是否为脏页？
                ├── 是 → 写回磁盘
                └── 否 → 直接丢弃
                    ↓
              从磁盘读取目标页面
                    ↓
              更新页表
                    ↓
              恢复进程
                    ↓
              重新执行原来的指令
```

如果物理内存已经满了，操作系统还需要先选择一个页面淘汰。

### 淘汰算法

- 最佳页面置换算法 OPT。淘汰未来最长时间不会被访问的页面。实际系统无法知道程序未来会访问哪些页面。

  因此 OPT 无法真正实现。只是作为一个评价的指标。

- 先进先出算法 FIFO。淘汰最早进入物理内存的页面。

- 最近最久未使用算法 LRU。淘汰最长时间没有被访问的页面。

- 时钟页面置换算法 Clock。利用页表项中的访问位，近似判断哪些页面最近没有被使用。当发生页面置换时，检查指针当前指向的页面。如果访问位为 0，说明这个页面最近没有被访问，可以淘汰，否则不淘汰。就是给一个机会。

- 最不常用算法 LFU。淘汰访问次数最少的页面。

## 八、修改位和访问位有什么用

进行页面淘汰，需要判断：

1. 哪些页面最近很少使用；
2. 哪些页面被修改过。

### 访问位

页面被读取或写入后，访问位会被设置。

作用：

> 帮助操作系统判断哪些页面最近使用过。

最近没使用的页面，更适合被淘汰。

### 修改位

页面被写入后，修改位会被设置，也叫脏位。

作用：

> 判断页面淘汰前是否需要写回磁盘。







## 九、缺页异常不一定是程序出错

需要区分三种情况。

### 1. 次要缺页错误

页面已经在物理内存中，只是当前进程的页表还没有建立映射。

处理方式：

```
补上映射关系
```

不需要读取磁盘，速度相对较快。

### 2. 主要缺页错误

页面不在物理内存中，需要从磁盘读取。

处理方式：

```
从磁盘加载页面
```

因为磁盘远慢于内存，所以开销很大。

### 3. 非法地址访问

程序访问了根本不存在或无权访问的地址。

例如：

```
int* p = nullptr;
*p = 10;
```

这种情况无法通过加载页面修复，操作系统通常会终止程序，并报告：

```
Segmentation Fault
```

所以：

> 缺页异常可能只是正常的内存调度；段错误才通常代表程序访问了非法地址。



## 分页

### 分页产生的问题

- 一个是慢，可以用MMU和TLB解决一下
- 一个是多

```
虚拟地址空间：4GB
页面大小：4KB
```

页的数量大约是：

```
4GB ÷ 4KB = 约 100 万页
```

每个进程都需要记录约 100 万个页表项，即使这个进程实际上只使用了很少的内存。

不管进程有没有使用某个虚拟地址，都要为整个虚拟地址空间准备页表项。

那么就用到多级页表解决页表太大的问题。

### 多级页表

把一个大页表拆成多层。

例如：

```
一级页表
   ↓
二级页表
   ↓
具体页表项
```

只有某段虚拟地址真正被使用时，才创建对应的二级页表。

因此，多级页表节省空间的原因是：

> **没有使用的虚拟地址范围，不需要建立对应的下级页表。**



## 分段

程序在逻辑上并不是一整块没有区别的数据，而是由不同部分组成的：

```
代码
全局变量
堆
栈
动态库
```

不同的部分可能的权限不同，职责不同，数据不同，要是混在一起就很麻烦，也很不方便，于是分段是在这种场景下解决问题的。

分段解决的是：

> 如何按照程序的逻辑结构管理内存。

分段和分页是两套不同的机制。

之前一般是有个段基址存在的，访问不同的数据给一个不同的段基址。但是现在不怎么用这个机制了，现在寄存器已经足够宽，CPU 可以直接保存完整的虚拟地址：

```
0x00007fff12345678
```

已经不需要：

```
段基址 + 小偏移
```

来拼出一个大地址。



# Linux可执行文件如何装载进虚拟内存

源代码通过预处理，编译，汇编，链接后形成可执行文件，因为计算机的操作系统的启动程序是写死在硬件上的，每次计算机上电时，都将自动加载启动程序，之后的每一个程序，每一个应用，都是不断的 fork 出来的新进程。那么我们的可执行文件，以linux 系统为例，也是由shell 进程 fork 出一个新进程，在新进程中调用exec函数装载我们的可执行文件并执行。

1. execve()。当shell中敲入执行程序的指令之后，shell进程获取到敲入的指令，并执行execve()函数，该函数的参数是敲入的可执行文件名和形参，还有就是环境变量信息。execve()函数对进程栈进行初始化，即压栈环境变量值，并压栈传入的参数值，最后压栈可执行文件名。初始化完成后调用 sys_execve()

2. sys_execve()。该函数进行一些参数的检查与复制，而后调用 do_execve()

3. do_execve()。该函数在当前路径与环境变量的路径中寻找给定的可执行文件名，找到文件后读取该文件的前128字节。读取这128个字节的目的是为了判断文件的格式，每个文件的开头几个字节都是魔数，可以用来判断文件类型。读取了前128字节的文件头部后，将调用 search_binary_handle()

4. search_binary_handle()。该函数将去搜索和匹配合适的可执行文件装载处理程序。Linux 中所有被支持的可执行文件格式都有相应的装在处理程序。以Linux 中的ELF 文件为例，接下来将会调用elf 文件的处理程序：load_elf_binary()

5. load_elf_binary()。

   该函数执行以下三个步骤:

   a）创建虚拟地址空间：实际上指的是建立从虚拟地址空间到物理内存的映射函数所需要的相应的数据结构。（即创建一个空的页表）

   b）读取可执行文件的文件头，建立可执行文件到虚拟地址空间之间的映射关系

   c）将CPU指令寄存器设置为可执行文件入口（虚拟空间中的一个地址）

   load_elf_binary()函数执行完毕，事实上装载函数执行完毕后，可执行文件真正的指令和数据都没有被装入内存中，只是建立了可执行文件与虚拟内存之间的映射关系，以及分配了一个空的页表，用来存储虚拟内存与物理内存之间的映射关系。

6. 程序返回到execve()中。此时从内核态返回到用户态，且寄存器的地址被设置为了ELF 的入口地址，于是新的程序开始启动，发现程序入口对应的页面并没有加载（因为初始时是空页面），则此时引发一个缺页错误，操作系统根据可执行文件和虚拟内存之间的映射关系，在磁盘上找到缺的页，并申请物理内存，将其加载到物理内存中，并在页表中填入该虚拟内存页与物理内存页之间的映射关系。之后程序正常运行，直至结束后回到shell 父进程中，结束回到 shell。



# 说一说内存对齐

- 由一个例子引出内存对齐

  ```c
  //32位系统
  #include<stdio.h>
  struct{
      int x;
      char y;
  }s;
  
  int main()
  {
      printf("%d\n",sizeof(s);  // 输出8
      return 0;
  }
  ```

  上述代码实际得到的值是8byte，这就是内存对齐所导致的。

  > 从理论上来讲，任何类型的变量可以从任意地址开始存放。但是实际上计算机对基本数据类型在内存中的存放位置有限制，会要求数据首地址的值是某个数（通常是4或8）的整数倍，这就是内存对齐。

- 为什么要内存对齐呢？

  计算机的内存是以字节为单位的，但是大部分处理器并不是按照字节块来存取内存的。计算机有个内存存取粒度的概念，就是说一般以2字节，4字节，8字节这样的单位来存取内存。

  性能原因：加入没有内存对齐机制，数据可以任意存放。地址排列为01234567现在读取一个int型变量，这个变量存放地址从1开始，那我们从0字节开始找，找到1后读取第一个4字节，把0扔掉，然后从地址4开始读下4个字节，扔掉567地址，int变量就存储在1234这里，可以看到这样很浪费开销，因为访问了两次内存。

- 内存对齐的规则

  对其规则如下：

  1. 基本类型的对齐值就是sizeof值。如果该成员是c++自带类型如int、char、double等，那么其对齐字节数=该类型在内存中所占的字节数；如果该成员是自定义类型如某个class或者struct，那个它的对齐字节数 = 该类型内最大的成员对齐字节数
  2. 结构体。结构体本身也要对齐，按照最大成员长度来参照的。
  3. 编译器可以设置最大对齐值，gcc中默认是#pragma pack(4)。但是类型的实际对齐值与默认对齐值取最小值来
  3. 如果设置了对齐字节数，就另说。①如果定义的字节数为1，就是所有默认字节数直接相加。②定义的字节数大于任何一个成员大小时候，不产生任何效果。如果定义的对齐字节数大于结构体内最小的，小于结构体内最大的话，就按照定义的字节数来计算



# 内存空间的堆和栈的区别是什么？



## 1. **概念与用途**

| 内存区域        | 用途                                                         |
| --------------- | ------------------------------------------------------------ |
| **栈（Stack）** | 由操作系统自动分配，用于存放函数参数、局部变量、返回地址等。数据的生命周期随着函数执行结束而结束。 |
| **堆（Heap）**  | 由程序员手动分配和释放（如 `malloc`/`free` 或 `new`/`delete`），用于存储动态分配的对象或数据。若程序不回收，操作系统在程序结束时自动回收。 |





**内存为什么要分堆栈在编程里，要是全部只用堆或者全部只用栈可以吗**

**原因**：

- 栈用于存储程序初期设定的变量，位置固定，访问快速。
- 堆用于存储运行结果和动态数据，长度可变。
- 两者生长方向相反，便于利用连续内存空间并避免冲突。

**全部用栈或全部用堆的问题**：

- 全用栈：难以满足动态数据需求，栈空间有限，容易溢出。
- 全用堆：分配效率低，频繁申请和释放容易产生碎片，管理复杂。

**结论**：分堆栈是为了**效率和灵活性兼顾**。



# 进程虚拟空间是怎么布局的？进程内存模型

# Linux 32 位进程虚拟空间布局（高地址 → 低地址）

```
+--------------------+ 0xFFFFFFFF
| 内核空间           | 内核代码和数据
+--------------------+
| 栈区（Stack）      | 函数局部变量、函数调用信息（栈帧）、临时计算结果
+--------------------+
| 内存映射段（mmap） | 文件映射、动态库加载、共享内存
+--------------------+
| 堆（Heap）         | 动态分配内存，字节对齐，可能产生碎片，由应用程序管理
+--------------------+
| BSS段              | 未初始化或初始化为0的全局/静态变量，OS清零初始化
+--------------------+
| 数据段（Data）     | 已初始化的全局/静态变量，可读写
+--------------------+
| 代码段（Text）     | 程序机器指令，可执行代码，通常可共享
+--------------------+
| 保留区（NULL区域） | 地址空间最低端，未映射，防止空指针访问
+--------------------+ 0x00000000
```

------

## 1. **栈区（Stack）**

- 存储函数局部变量、函数参数、返回地址（栈帧）。
- 临时存储计算结果和 `alloca` 分配的栈内存。
- 栈自高地址向低地址生长。

------

## 2. **内存映射段（mmap）**

- 内核将文件直接映射到内存，方便高效文件 I/O。
- 常用于加载动态共享库或映射大文件。

------

## 3. **堆（Heap）**

- 由程序动态分配（`malloc`/`new`）和释放。
- 内存对齐，使用链表管理空闲块。
- 释放的内存可重用；不释放时程序结束由操作系统回收。
- 堆自低地址向高地址生长。

------

## 4. **BSS 段**

- 存储未初始化或初始化为 0 的全局/静态变量。
- 不占用可执行文件空间，由操作系统加载时清零。

## 5. **数据段（Data）**

- 存储已初始化的全局/静态变量。
- 占用可执行文件空间，读取时可能触发缺页异常。

**BSS vs Data**：

| 特性         | BSS                | Data           |
| ------------ | ------------------ | -------------- |
| 文件占用     | 不占               | 占用           |
| 初始化       | 0（OS清零）        | 程序指定初值   |
| 物理内存分配 | 访问时映射全零页面 | 访问时分配页面 |

------

## 6. **代码段（Text）**

- 存放可执行机器指令。
- 通常只读，可共享，减少内存占用。

------

## 7. **保留区（NULL区域）**

- 虚拟地址空间最低端，未分配物理地址。
- 防止空指针或非法低地址引用。





# 系统调用和进程上下文切换的区别

系统调用过程中，并不会涉及到虚拟内存等进程用户态的资源，也不会切换进程。主要是让用户程序访问受保护的硬件资源或内核功能（如文件操作、网络、进程管理）。

进程上下文切换，是指从一个进程切换到另一个进程运行；而系统调用过程中一直是同一个进程在运行。



# 用户态、内核态、系统调用

这三个概念要连起来理解：

> 程序平时运行在用户态；需要操作硬件或系统资源时，通过系统调用进入内核态；内核完成操作后，再返回用户态。

```
用户态程序
    │
    │ 系统调用
    ▼
操作系统内核
    │
    │ 返回结果
    ▼
用户态程序
```

## 用户态和内核态切换时发生什么

发生切换时，CPU 通常需要保存当前执行现场，例如：

- 当前指令地址
- 栈指针
- CPU 寄存器
- 当前权限状态

然后：

1. 从用户栈切换到内核栈。
2. 跳转到内核入口。
3. 执行内核代码。
4. 恢复用户态现场。
5. 回到用户程序原来的位置继续执行。

因此系统调用比普通函数调用开销更大。







# 什么是大端字节，什么是小端字节？如何转换字节序？

大端序，小端序是计算机存储数据的两种方式。

大端字节序：高位字节在前，低位字节在后，符合人类读写数值的习惯（参考普通的十进制数）

小端字节序：低位字节在前，高位字节在后。



- 为什么要有大小端字节序？统一不行吗？

  ### **小端序的优势（Intel 用的）**

  1. **内存低地址放低字节 → 类型转换方便**
     - 比如 `int(4字节)` 转 `short(2字节)`，只要取低地址的前 2 个字节就行，不用调整字节顺序。
     - 因为低地址存的就是最低有效位，符合 C/C++ 类型转换时“直接截断低位”的逻辑。
  2. **CPU运算更高效**
     - CPU做加减运算时，通常是从低位字节开始算（因为进位要逐级传递）。
     - 小端布局保证了低位字节就在内存的低地址，取数时顺序和运算方式一致，更自然高效。

  ------

  ### **大端序的优势（Motorola、网络协议常用）**

  1. **更符合人类习惯**
     - 写数字 1234，我们总是把最高位写在前面。大端内存布局也是“最高字节在前”。
  2. **适合网络传输和文件存储**
     - 在通信或序列化时，数据的“顺序”非常重要。
     - 如果用大端，那么字节序和人类读写顺序一致，解析时直观。
     - 特别是符号位（最高位），放在第一个字节里，可以快速判断正负、比较大小。





- 转换字节序

  主要是针对主机字节序和网络字节序来说的。我们用的x86架构的处理器一般都是小端序存储数据，但是网络字节序是TCP/IP中规定好的数据表示格式，RFC1700规定使用“大端”字节序为网络字节序，独立于处理器操作系统。

  在Linux网络编程中，会使用下列C标准库函数进行字节之间的转换

  ```c
  #include <arpa/inet.h>
  
  uint32_t htonl(uint32_t hostlong);		//把uint32_t类型从主机序转换到网络序
  uint16_t htons(uint16_t hostshort);		//把uint16_t类型从主机序转换到网络序
  uint32_t ntohl(uint32_t netlong);		//把uint32_t类型从网络序转换到主机序
  uint16_t ntohs(uint16_t netshort);		//把uint16_t类型从网络序转换到主机序
  ```

- 如何判断本机是大端序还是小端序？

  ```c
  int i=1;   
  char *p=(char *)&i;   
  if(*p == 1)     
      printf("小端模式"); //小端序是低位字节在前，高位字节在后
  else // (*p == 0)
      printf("大端模式");
  ```

# 共享内存

## 为什么需要共享内存

参考进程通信方式和虚拟内存

虚拟内存导致不同程序拿到了虚拟地址，对应的物理内存是不同的，因此进程通信有困难，这时候共享内存把两个虚拟地址映射到同一块物理地址，就好通信了。

## 共享内存所在的位置

通常可以将进程地址空间简化为：

```
高地址
┌────────────────────┐
│        栈           │
│         ↓           │
├────────────────────┤
│                    │
│ mmap 映射区域       │ ← 共享内存、动态库、文件映射等
│                    │
├────────────────────┤
│         ↑           │
│        堆           │
├────────────────────┤
│ BSS / DATA / TEXT   │
└────────────────────┘
低地址
```

位置其实也不固定，共享内存会表现为进程虚拟地址空间中的一个独立映射区域，具体虚拟地址并不固定。



## Linux 中的两类共享内存

### 1. System V 共享内存

主要接口：

```
shmget();   // 创建或获取共享内存段
shmat();    // 把共享内存段连接到当前进程
shmdt();    // 取消连接
shmctl();   // 查询、设置或标记删除
```

基本过程：

```
shmget 创建共享内存段
          ↓
shmat 映射到进程 A
          ↓
shmat 映射到进程 B
          ↓
两个进程访问同一份数据
```

### 2. POSIX 共享内存

主要接口：

```
shm_open();    // 创建或打开共享内存对象
ftruncate();   // 设置共享内存大小
mmap();        // 映射到当前进程
munmap();      // 解除映射
shm_unlink();  // 删除共享内存对象的名字
```

基本过程：

```
shm_open 创建共享内存对象
             ↓
ftruncate 设置大小
             ↓
mmap(..., MAP_SHARED, ...)
             ↓
多个进程映射同一个对象
```





# malloc是如何实现内存管理的

## 一、先建立整体认识

`malloc` 不是系统调用，而是 C 标准库提供的**用户态内存分配器接口**。

它处在应用程序和操作系统之间：

```
程序调用 malloc
        ↓
glibc 内存分配器查找可复用的空闲块
        ↓
找到：直接返回
没找到：通过 brk 或 mmap 向内核申请更多虚拟内存
        ↓
切割出合适的内存块返回给程序
```

因此，`malloc` 主要负责两件事：

1. 向操作系统批量申请内存；
2. 在用户态对这些内存进行切割、缓存、复用和合并。

`malloc` 返回的是一段**连续的虚拟地址空间**，不代表对应的物理内存也是连续的。Linux 通常会在程序真正访问这些页面时，通过缺页异常分配物理页。



## 二、malloc 为什么不直接调用系统调用

假如有频繁的malloc操作，如果malloc 直接调用系统调用，那就是每次都切换内核态，开销比较大。

所以malloc 通常先向操作系统取得一大片内存，然后自己在用户态管理。

```
操作系统提供的一大片内存
┌────────────────────────────────────┐
│ chunk A │ chunk B │ 空闲 chunk │ top │
└────────────────────────────────────┘
             ↑
        malloc 自己管理
```

这种模式可以理解为一种通用内存池。



## malloc 如何向操作系统取得内存

### 1. brk

进程的数据段末尾有一个位置称为 **program break**。

```
低地址
┌───────────────┐
│ 已使用的数据段 │
├───────────────┤
│ malloc 堆空间  │
├───────────────┤ ← program break
│ 尚未映射的空间 │
└───────────────┘
高地址
```

将 program break 向高地址移动，相当于扩大进程的堆；向低地址移动，则可以缩小堆。

```
int brk(void* addr);
void* sbrk(intptr_t increment);
```

在 Linux 上，`sbrk()` 是基于 `brk` 系统调用实现的库函数。普通程序不应直接使用它们，而应使用 `malloc`。

### 2. mmap

`mmap` 可以创建匿名私有映射，为进程分配一块独立的虚拟地址区域：

```
mmap(
    nullptr,
    size,
    PROT_READ | PROT_WRITE,
    MAP_PRIVATE | MAP_ANONYMOUS,
    -1,
    0
);
```

glibc 通常会对较大的分配请求考虑使用 `mmap`。这类内存独立于传统的 brk 堆，释放时可以直接通过 `munmap` 解除映射。

但是不能简单记成：

```
小于128KB一定使用brk
大于128KB一定使用mmap
```

glibc 的 mmap 阈值默认会动态调整，初始值可能是 128KB，但会随着程序的分配和释放行为发生变化，也可以通过参数配置。



## 四、malloc 管理内存的基本单位：chunk

可以认为取得了一大块内存后，分成了一个个小的chunk。彼此用链表进行链接。当申请内存，就给一块儿，释放的时候再链接回来。



## 五、空闲 chunk 如何组织

有多种缓存和链表结构来管理这些chunk，内容比较多和繁杂，不算入重点内容。



## 面试总结

好复杂

malloc 是一个运行在用户态的内存分配器。

它先通过 brk 或 mmap 从操作系统取得较大的虚拟内存区域，再把这些区域划分成 chunk。每个 chunk 带有大小和状态等元数据。

释放后的 chunk 不一定立即归还操作系统，而是进入 tcache、fastbin、unsorted bin、small bin 或 large bin，供后续 malloc 复用。malloc 会在适当的时候切割大 chunk、合并相邻空闲 chunk，或者从 top chunk 中分配。

当现有内存无法满足请求时，malloc 才会再次通过 brk 或 mmap 向操作系统申请内存。独立 mmap 分配通常可以在 free 时直接解除映射，而 brk 堆中间的空闲内存通常只能留给 malloc 继续复用。











# 信号量和互斥量的区别？

## ① **互斥量（Mutex）**

- **用途**：保证**同一时刻只有一个线程/进程**能访问共享资源。
- **特点**：
  - 只有两种状态：锁定 / 未锁定。
  - 谁加锁，谁必须解锁（所有权严格）。
  - 本质是 **排他锁**。

👉 **比喻**：厕所里只有一个坑，门上有个锁，进去的人必须锁门，出来的人必须开锁，下一个人才可以进。

------

## ② **信号量（Semaphore）**

- **用途**：可以控制**多个线程/进程**对资源的并发访问数量。

- **特点**：

  - 是一个计数器。

  - > 0 → 表示还有资源可以用，`P操作(等待)` 时计数减一；
    >  =0 → 表示没资源了，调用者阻塞等待；
    >  `V操作(释放)` 时计数加一。

  - 没有“所有权”，谁都可以 `P` 或 `V`。

- 可以实现：

  - **二值信号量（值只能是 0/1）** → 其实就和互斥量差不多。
  - **多值信号量** → 可以允许 N 个线程同时访问。

👉 **比喻**：食堂有 5 个饭盒，来的人先拿一个，拿完 5 个后，其他人就得等有人吃完放回去。





# 写时拷贝底层原理

## 1. 为什么需要写时拷贝

Linux 中，`fork()` 用来创建一个子进程。

从使用效果上看，子进程刚创建出来时，拥有一份与父进程相同的虚拟地址空间：

- 相同的代码
- 相同的全局变量
- 相同的堆数据
- 相同的栈数据

但父子进程是两个独立进程。后续父进程修改自己的变量，不应该影响子进程；子进程修改数据，也不应该影响父进程。

最直接的实现方式是：

> `fork()` 时立即复制父进程使用的所有内存。

假设父进程占用了 1 GB 内存，那么创建子进程时，就需要再申请大量物理内存，并复制这 1 GB 数据。

这样存在两个问题：

1. **复制开销很大**
   `fork()` 的执行时间会随着父进程内存的增加而增加。
2. **很多复制可能完全没有必要**
   子进程创建后，经常会立即调用 `exec()`，用新程序替换当前地址空间。刚刚复制的数据还没使用，就被全部丢弃了。

因此，Linux 使用写时拷贝来推迟内存复制：

> `fork()` 时先共享物理页，只有某个进程真正修改页面时，才为它复制一份。



## 写时拷贝需要的东西

因为需要先共享物理页，所以需要虚拟内存映射。为了避免一个进程修改直接影响另外的进程，所以先给原本可写的页面设置为只读。当这个进程想写的时候，触发缺页异常（这里只是页面存在于物理内存中，但当前操作违反了页表权限。）然后再让内核判断，哦只是非法写入。这之后就可以执行写时拷贝了。



## 8. 完整流程

```
父进程调用 fork()
        ↓
创建子进程和子进程页表
        ↓
父子进程页表指向相同物理页
        ↓
相关私有可写页暂时设为只读
        ↓
父子进程只读访问
        ↓
不需要复制物理页
        ↓
某个进程尝试写入
        ↓
CPU 发现页面不可写
        ↓
触发缺页异常
        ↓
内核判断为写时拷贝
        ↓
检查物理页是否仍被共享
        ↓
被共享：申请新页并复制内容
只有一个使用者：直接恢复可写权限
        ↓
修改当前进程页表
        ↓
重新执行写指令
```



# 栈区分配内存快还是堆区分配内存快 ？

栈区分配内存比堆区分配快很多。

------

### 1. **栈区内存分配**

- 栈是**连续的内存区域**，编译器已经分配好空间。
- 分配/释放就是**移动栈指针（SP）**，代价极小。
- 生命周期：函数调用时分配，函数返回时自动释放。

👉 类似“把书放在书堆顶”，放一本书（分配）和拿走一本书（释放）都很快。

------

### 2. **堆区内存分配**

- 堆由程序员申请（`malloc/new`）、释放（`free/delete`）。
- 需要调用**系统库函数**，涉及**查找空闲块、分割、合并碎片**等操作。
- 分配和释放都比较慢，而且可能产生**内存碎片**。

👉 类似“去仓库找个空位放东西”，要找、登记、腾位置，慢得多。

# Cache

## 1. Cache 是什么

Cache 是位于 **CPU 和主存之间的高速缓存**，通常由速度较快的 SRAM 构成。

它的作用是：

> 缓存 CPU 最近或经常访问的数据，减少访问主存的次数，提高程序运行速度。

Cache 中存放的**不是页表**，而是从主存复制过来的普通数据或指令。

例如主存中有：

```
int array[4] = {10, 20, 30, 40};
```

CPU 要读取 `array[0]` 时，不一定只把这一个 `int` 的 4 字节放入 Cache，而是把它附近的一整段连续数据放进去。

这段数据称为：

> **Cache Line，缓存行**



Cache 的特点：

- 速度快
- 容量小
- 成本高

主存的特点：

- 速度较慢
- 容量大
- 成本较低

Cache 能发挥作用，主要依赖程序访问数据的**局部性**：

- **时间局部性**：刚访问的数据，近期可能再次访问。
- **空间局部性**：访问某个地址后，附近地址也可能被访问。

------

## 2. Cache 的工作过程

CPU 访问一个内存地址时，需要完成两件事：

1. 通过 MMU、TLB 将虚拟地址转换成物理地址。
2. 根据地址查找 Cache 中是否保存了对应数据。

查找结果分为两种：

### Cache 命中

Cache 中存在对应的数据，CPU 直接从 Cache 读取，不需要访问主存。

### Cache 未命中

Cache 中没有对应的数据，需要从主存读取。

读取后，通常会把数据所在的整个 **Cache Line** 加载到 Cache 中，方便后续访问。

基本过程：

```text
CPU 发出地址
    ↓
查询 Cache
    ↓
命中：直接读取数据
未命中：从主存加载数据到 Cache，再返回给 CPU
```

Cache Line 是 Cache 与主存之间传输数据的基本单位，通常包含连续的一段内存数据。

------

## 3. 多级 Cache

单级 Cache 容量有限，发生未命中时仍然需要等待主存，因此现代 CPU 通常采用多级 Cache：

```text
CPU
 ↓
L1 Cache
 ↓
L2 Cache
 ↓
L3 Cache
 ↓
主存
```

不同级别的特点：

| 级别 | 速度 | 容量 | 特点                   |
| ---- | ---- | ---- | ---------------------- |
| L1   | 最快 | 最小 | 通常每个 CPU 核心独享  |
| L2   | 较快 | 较大 | 通常每个核心独享       |
| L3   | 较慢 | 最大 | 通常由多个核心共享     |
| 主存 | 最慢 | 最大 | 保存程序运行所需的数据 |

访问时会优先查找 L1，未命中再查找 L2、L3，最后才访问主存。

------

## 总结

Cache 是 CPU 和主存之间的高速缓存。

它通过保存近期可能再次访问的数据，减少 CPU 等待主存的时间。Cache 越靠近 CPU，速度越快、容量越小；越远离 CPU，速度越慢、容量越大。

fork()` 只在父进程中调用一次，但创建子进程后，父子进程都会从 `fork() 返回。

```
pid_t pid = fork();

if (pid > 0) {
    // 父进程
} else if (pid == 0) {
    // 子进程
} else {
    // 创建失败
}
```

返回值有三种情况：

| 返回值 | 所在进程 | 含义                       |
| ------ | -------- | -------------------------- |
| `> 0`  | 父进程   | 返回子进程的 PID           |
| `== 0` | 子进程   | 表示当前代码运行在子进程中 |
| `< 0`  | 父进程   | 创建子进程失败             |

## fork 后父子进程的内存关系

从程序角度看，子进程获得了父进程地址空间的一份副本，包括：

- 代码段；
- 全局数据区；
- 堆；
- 栈；
- 内存映射区域；
- 页表映射关系。

因此，刚执行完 `fork()` 时，父子进程中的变量通常具有：

- 相同的值；
- 相同的虚拟地址；
- 最初可能对应相同的物理内存页。

但是只是父子进程的内存内容看起来相同；创建完成后，双方分别拥有独立的地址空间，普通变量的修改互不影响。

## fork 后谁先执行

父进程和子进程谁先执行，**没有保证**。

fork 完成后，父子进程都会进入可运行状态，由操作系统调度器决定先运行谁：

```
可能父进程先执行
也可能子进程先执行
```

但是为了避免写时复制，一些内核或者策略可能会倾向于先调度子进程



## fork 与 exec 的常见组合

fork 负责创建子进程，exec 负责让子进程运行另一个程序。

典型流程：

```
父进程调用 fork
        ↓
创建子进程
        ↓
子进程调用 exec
        ↓
子进程地址空间被新程序替换
        ↓
父进程调用 wait 等待子进程
```

示例：

```
pid_t pid = fork();

if (pid == 0) {
    execl("/bin/ls", "ls", "-l", nullptr);

    // exec 成功后不会执行到这里
    perror("execl");
    _exit(1);
} else if (pid > 0) {
    waitpid(pid, nullptr, 0);
} else {
    perror("fork");
}
```

`exec()` 成功后：

- 原来的代码段被替换；
- 原来的堆和栈被替换；
- 加载新程序的代码和数据；
- PID 通常保持不变。

所以 exec 并不是创建新进程，而是用新程序替换当前进程的内容。



## 父进程为什么要 wait

子进程退出后，内核还需要保存一部分信息，例如：

- 退出状态；
- 资源使用情况；
- PID 等进程信息。

这些信息需要父进程通过 `wait()` 或 `waitpid()` 回收。

如果子进程已经退出，但父进程一直不回收，子进程会成为**僵尸进程**。





# fork复制内部，为什么fork返回0？

> `fork()` 由父进程调用一次，但创建子进程后，父子进程都会从 `fork()` 后面继续执行，因此表现为返回两次。

> 系统调用返回值保存在寄存器里，内核让父进程的返回值寄存器保存子进程 PID，让子进程的返回值寄存器保存 0。

> 子进程返回 0 只是为了区分父子进程，与链表、是否拥有子进程没有关系。

> fork 后父子进程谁先执行没有保证，必须通过 `waitpid`、管道、信号量等机制控制顺序。



# 锁是什么？

**本质思想**

并发编程中，为了保证数据操作的一致性，操作系统引入了锁机制，为了保证临界区代码的安全。锁其实是一种思想

锁的本质就是计算机中的一块内存。当这块内存空间被赋值为1的时候表示加锁了，当被赋值为0的时候表示解锁了，当然这块内存空间在哪里并不重要。多个线程抢占一个锁，就是要把这块内存赋为1。

在单核的情况下，关闭 CPU 中断，使其不能暂停当前请求而处理其他请求，从而达到赋值“锁”对应的内存空间的目的。

在多核的情况下，使用锁总线和缓存一致性技术（详情看这里），可以实现在单一时刻，只有某个CPU里面某一个核能够赋值“锁”对应的内存空间，从而达到锁的目的。

> 锁总线和缓存一致性
>
> 随着多核时代的到来，并发操作已经成了很正常的现象，操作系统必须要有一些机制和原语，以保证某些基本操作的原子性，比如处理器需要保证读一个字节或写一个字节是原子的，那么它是如何实现的呢？有两种机制：**总线锁定、缓存一致性**。
>
> CPU 和物理内存之间的通信速度远慢于 CPU 的处理速度，所以 CPU 有自己的内部缓存，根据一些规则将内存中的数据读取到内部缓存中来，以加快频繁读取的速度。那么这样就会造成cpu寄存器中的值和内存中的值出现不匹配的现象。（比如两核，i=0，第一个核i+1，第二个核取i的时候i还是0）
>
> **总线锁定机制：**在 CPU1 要做 i++ 操作的时候，其在总线上发出一个 LOCK 信号，其他处理器就不能操作缓存了该变量内存地址的缓存，也就是阻塞了其他CPU，使该处理器可以独享此共享内存。
>
> **缓存一致性：**当某块 CPU 对缓存中的数据进行操作了之后，就通知其他 CPU 放弃储存在它们内部的缓存，或者从主内存中重新读取



# 锁的开销

[参考](https://www.cnblogs.com/cposture/p/10761396.html)

**所有锁的本质：**

我们针对的是多线程环境下的锁机制，基于linux做测试。每种编程语言提供的锁机制都不太一样，不过无论如何，最终都会落实到两种机制上，**一是处理器提供的原子操作指令（现在一般是CAS—compare and swap），处理器会用轮询的方式试图获得锁，在处理器（包括多核）架构里这是必不可少的机制；二是内核提供的锁系统调用，在被锁住的时候会把当前线程置于睡眠（阻塞）状态。**

实际上我们在编程的时候并不会直接调用这两种机制，而是使用编程语言所带函数库里的锁方法，锁方法内部混合使用这两种机制。以pthread库（NPTL）的pthread_mutex来举例，一把锁本质上只是一个int类型的变量，占用4个字节内存并且内存边界按4字节对齐。加锁的时候先用trylock方法（内部使用的是CAS指令）来尝试获得锁，如果无法获得锁，则调用系统调用sys_futex来试图获得锁，这时候如果还不能获得锁，当前线程就会被阻塞。(**futex的知识**)

**所以很容易得到一个结论，如果锁不存在冲突，每次获得锁和释放锁的处理器开销仅仅是CAS指令的开销，在x86-64处理器上，这个开销只比一次内存访问（无cache）高一点（大概是1.3倍）。一般的电脑上一次没有缓存的内存访问大概是十几纳秒**

**测试：**

无冲突的时候：运行了 10 亿次，平摊到每次加锁/解锁操作大概是 14ns 

锁冲突的情况：运行的结果是双核机器上消耗大约3400ns，所以锁冲突的开销大概是不冲突开销的两百倍了，相差出乎意料的大。

**锁的开销**

总结：锁的开销有好几部分，分别是：线程上下文切换的开销，调度器开销（把线程从睡眠改成就绪或者把就运行态改成阻塞），还有后续上下文切换带来的缓存不命中开销，跨处理器调度的开销等等。

**锁的优化：**

从上面可以知道，真正消耗时间的不是上锁的次数，而是锁冲突的次数。减少锁冲突的次数才是提升性能的关键。使用更细粒度的锁，可以减少锁冲突。这里说的粒度包括时间和空间，比如哈希表包含一系列哈希桶，为每个桶设置一把锁，空间粒度就会小很多－－哈希值相互不冲突的访问不会导致锁冲突，这比为整个哈希表维护一把锁的冲突机率低很多。减少时间粒度也很容易理解，加锁的范围只包含必要的代码段，尽量缩短获得锁到释放锁之间的时间，最重要的是，绝对不要在锁中进行任何可能会阻塞的操作。使用读写锁也是一个很好的减少冲突的方式，读操作之间不互斥，大大减少了冲突。

假设单向链表中的插入/删除操作很少，主要操作是搜索，那么基于单一锁的方法性能会很差。在这种情况下，应该考虑使用读写锁，即 pthread_rwlock_t，这么做就允许多个线程同时搜索链表。插入和删除操作仍然会锁住整个链表。假设执行的插入和搜索操作数量差不多相同，但是删除操作很少，那么在插入期间锁住整个链表是不合适的，在这种情况下，最好允许在链表中的分离点（disjoint point）上执行并发插入，同样使用基于读写锁的方式。在两个级别上执行锁定，链表有一个读写锁，各个节点包含一个互斥锁，在插入期间，写线程在链表上建立读锁，然后继续处理。在插入数据之前，锁住要在其后添加新数据的节点，插入之后释放此节点，然后释放读写锁。删除操作在链表上建立写锁。不需要获得与节点相关的锁；互斥锁只建立在某一个操作节点之上，大大减少锁冲突的次数。

锁本身的行为也存在进一步优化的可能性，sys_futex系统调用的作用在于让被锁住的当前线程睡眠，让出处理器供其它线程使用，既然这个过程的消耗很高，也就是说如果被锁定的时间不超过这个数值的话，根本没有必要进内核加锁——释放的处理器时间还不够消耗的。sys_futex的时间消耗够跑很多次 CAS 的，也就是说，对于一个锁冲突比较频繁而且平均锁定时间比较短的系统，一个值得考虑的优化方式是先循环调用 CAS 来尝试获得锁（这个操作也被称作自旋锁），在若干次失败后再进入内核真正加锁。当然这个优化只能在多处理器的系统里起作用（得有另一个处理器来解锁，否则自旋锁无意义）。在glibc的pthread实现里，通过对pthread_mutex设置PTHREAD_MUTEX_ADAPTIVE_NP属性就可以使用这个机制。

> 注：CAS指令是线程数据同步的原子指令。



# 什么是futex

linux的pthreads mutex采用futex实现

Futex 是 Fast Userspace Mutexes 的缩写，现在锁的机制一般使用这个，内核态和用户态的混合机制。其设计思想其实不难理解。

在传统的 Unix 系统中，System V IPC（inter process communication），如 semaphores，msgqueues，sockets 等进程间同步机制都是对一个**内核对象**操作来完成的，这个内核对象对要同步的进程都是可见的，其提供了共享的状态信息和原子操作，用来管理互斥锁并且通知阻塞的进程。当进程间要同步的时候必须要通过系统调用（如semop()）在内核中完成。比如进程A要进入临界区，先去内核查看这个对象，有没有别的进程在占用这个临界区，出临界区的时候，也去内核查看这个对象，有没有别的进程在等待进入临界区，然后根据一定的策略唤醒等待的进程。同时经研究发现，很多同步是无竞争的，即某个进程进入互斥区，到再从某个互斥区出来这段时间，常常是没有进程也要进这个互斥区或者请求同一同步变量的。但是在这种情况下，这个进程也要陷入内核去看看有没有人和它竞争，退出的时侯还要陷入内核去看看有没有进程等待在同一同步变量上，有的话需要唤醒等待的进程。这些不必要的系统调用(或者说内核陷入)造成了大量的性能开销。为了解决这个问题，Futex就应运而生。

为了解决上述这个问题，Futex 就应运而生，Futex 是一种用户态和内核态混合的同步机制。首先，同步的进程间通过 mmap 共享一段内存，futex 变量就位于这段共享的内存中且操作是原子的，当进程尝试进入互斥区或者退出互斥区的时候，先去查看共享内存中的 futex 变量，如果没有竞争发生，就不用再执行系统调用了。当通过访问 futex 变量后进程发现有竞争发生，则还是得执行系统调用去完成相应的处理（wait 或者 wake up）。简单的说，futex 就是通过在用户态的检查，（motivation）如果了解到没有竞争就不用陷入内核了，大大提高了 low-contention 时候的效率。

mutex 是在 futex 的基础上用的内存共享变量来实现的，如果共享变量建立在进程内，它就是一个线程锁，如果它建立在进程间共享内存上，那么它是一个进程锁。pthread_mutex_t 中的 `_lock` 字段用于标记占用情况，先使用CAS判断`_lock`是否占用，若未占用，直接返回。否则，通过`__lll_lock_wait_private` 调用`SYS_futex `系统调用迫使线程进入沉睡。 CAS是用户态的 CPU 指令，若无竞争，简单修改锁状态即返回，非常高效，只有发现竞争，才通过系统调用陷入内核态。所以，FUTEX是一种用户态和内核态混合的同步机制，它保证了低竞争情况下的锁获取效率。



# 中断相关知识点

## 中断解决什么问题

CPU执行程序时，外部设备和程序内部都可能发生一些必须立即处理的事件，例如：

- 网卡收到了数据包；
- 磁盘完成了读写；
- 定时器到期；
- 程序访问了尚未映射的虚拟内存；
- 用户程序请求内核提供服务；
- 其他CPU要求当前CPU执行某项操作。

CPU需要暂时停下当前工作，处理这些事件，然后再继续执行原来的程序。

这个过程就是中断机制。

中断机制解决的核心问题是：

> 当系统发生特殊事件时，如何让CPU及时转去处理，同时又能在处理完成后继续原来的工作。

## 为什么不能轮询检查数据到了或者完成了任务？

因为这会占用CPU，而且大部分检查都没结果。这里的中断能在任务完成后主动通知CPU，让CPU来处理数据，提高CPU的利用率



## 中断事件的主要来源

### 1. 外部设备产生的中断 

例如：

- 网卡收到数据包；
- 磁盘完成IO；
- 键盘被按下；
- 定时器到期。

### 2. CPU之间产生的中断

一个CPU可以向另一个CPU发送中断

### 3. CPU执行指令时发现异常

CPU异常又可以分为三类。

- 故障。异常可能被修复，修复后重新执行刚才的指令。（缺页异常）
- 陷阱。当前指令已经执行完成，异常处理结束后从下一条指令继续执行。（调试断点；单步调试。）
- 中止。发生了严重错误，通常无法恢复。



## 流程

以网卡收到数据为例：

```
1. 外设发
生事件
   网卡收到数据包。

2. 外设发出中断
   网卡通知中断控制器，再由中断控制器通知CPU。

3. CPU暂停当前程序
   CPU执行完当前指令，保存当前程序的寄存器、执行位置等现场。

4. 进入内核
   如果CPU原本在用户态，就切换到内核态和内核栈。

5. 查找处理入口
   CPU根据中断向量号查询IDT，找到对应的中断入口。

6. 调用设备驱动
   Linux根据IRQ找到设备驱动注册的中断处理函数。

7. 处理紧急工作
   驱动确认中断、读取设备状态、清除中断标志。

8. 延后耗时工作
   较复杂的工作交给softirq、NAPI或workqueue处理。

9. 检查是否需要调度
   中断可能唤醒其他进程，内核决定是否切换进程。

10. 恢复现场
    恢复寄存器和执行位置，继续运行原程序。
```



# Linux零拷贝技术

## 一、什么是零拷贝

零拷贝（Zero-Copy）是一类 I/O 优化技术。

它的目标是：

> 在文件、内存和网络设备之间传输数据时，减少用户态与内核态之间的数据复制，以及 CPU 参与的数据复制。

注意，主要是减少了由 CPU 完成的数据复制，适合 FTP、HTTP 文件服务器、反向代理等需要传输大量数据的场景。



## 二、为什么需要零拷贝

假设服务器需要读取磁盘文件，然后通过 Socket 发送给客户端，传统代码通常是：

```
read(file_fd, buffer, size);
write(socket_fd, buffer, size);
```

数据传输过程如下：

```
磁盘
  │
  │ DMA 拷贝
  ▼
内核页缓存 Page Cache
  │
  │ CPU 拷贝
  ▼
用户空间 buffer
  │
  │ CPU 拷贝
  ▼
内核 Socket 发送缓冲区
  │
  │ DMA 拷贝
  ▼
网卡
```



#### 1、先回答一个问题，为什么read要经过用户空间

调用方式：

```
char buffer[4096];
read(file_fd, buffer, sizeof(buffer));
```

用户传进来的 `buffer` 位于用户空间，所以 `read()` 必须保证：

```
read 返回之后
buffer 中真的存在文件数据
```

因此数据必须从内核页缓存复制到用户缓冲区：



整个过程中包括：

- 2 次 DMA 拷贝；
- 2 次 CPU 拷贝；
- 2 次系统调用；
- 4 次用户态与内核态切换。



```
这里介绍一下DMA

DMA 是 Direct Memory Access，即直接内存访问。

CPU 告诉 DMA：
把磁盘中的这段数据传输到这块内存。

DMA 完成传输后：
通过中断通知 CPU。

因此，磁盘到内存、内存到网卡的数据传输，通常不需要 CPU 逐字节复制。
```



这里的 4 次切换分别是：

```
用户态 → 内核态：执行 read
内核态 → 用户态：read 返回

用户态 → 内核态：执行 write
内核态 → 用户态：write 返回
```

能看出来

1、内核状态的频繁改变，

2、一个数据先被CPU复制到用户buffer，又被复制到socket缓冲区

所以一眼能看出来不好的问题，为了解决这问题，就产生了零拷贝技术。作用就是解决上面这俩



## 三、零拷贝的方式

主要是消除掉到用户空间的这一层消耗

### 1、mmap+write

用mmap()，直接让用户空间的虚拟地址映射到文件对应的物理内存页。

数据路径为：

```
磁盘
  │ DMA
  ▼
内核页缓存
  │
  │ 用户空间通过虚拟地址访问同一批物理页
  │
  │ CPU 拷贝
  ▼
Socket 发送缓冲区
  │ DMA
  ▼
网卡
```

就减少了一次CPU拷贝的过程,只需要wirte的一次CPU拷贝就行了。

### 2、sendfile()

`sendfile()` 可以直接在内核中，把文件数据发送到 Socket。

`sendfile()` 的语义是：

> 用户程序不需要看到数据，请内核直接把文件内容发送到 Socket。

```
sendfile(socket_fd, file_fd, &offset, count);
```

这里用户已经明确告诉内核：

```
输入：这个文件
输出：这个 Socket
范围：从这个位置发送这么多字节
```

文件数据不需要进入用户空间。

基本数据路径为：

```
磁盘
  │ DMA
  ▼
内核页缓存
  │ CPU 拷贝
  ▼
Socket 发送缓冲区
  │ DMA
  ▼
网卡
```

这样内核仍然需要把数据从页缓存复制到 Socket 发送缓冲区，不过也还是减少了一次CPU拷贝过程

### 3、支持 Scatter/Gather 的 sendfile

现代 Linux 可以配合网卡的 Scatter/Gather DMA 功能进一步优化。

内核不再复制完整文件数据到 Socket 缓冲区，而是在 Socket 缓冲区中保存：

- 数据所在内存页的引用；
- 数据偏移量；
- 数据长度。

过程可以理解为：

网卡直接通过socket拿内存页信息发出去。

数据路径为：

```
文件数据已经在页缓存
        ↓
Socket 发送队列记录：
页引用 + 偏移量 + 长度
        ↓
网卡驱动生成 DMA 描述符
        ↓
网卡按地址从内存页读取数据
        ↓
发送到网络
```

此时通常包含：

- 2 次 DMA 传输；
- 0 次完整数据的 CPU 拷贝；
- 1 次系统调用；
- 2 次用户态与内核态切换。

这里仍然可能存在少量元数据处理，但不会复制完整的文件内容。

### 4、splice()

`splice()` 可以在两个文件描述符之间移动数据，而不需要把数据复制到用户空间。

但它有一个重要限制：

> `fd_in` 和 `fd_out` 中，至少有一个必须是管道。

因此，不能简单地直接执行：

```
普通文件 → Socket
```

通常需要通过管道中转：

```
文件 → 管道 → Socket
```

先创建管道：

```
int pipefd[2];
pipe(pipefd);
```

然后执行两次 `splice()`：

```
// 文件 → 管道
splice(
    file_fd,
    nullptr,
    pipefd[1],
    nullptr,
    size,
    SPLICE_F_MOVE
);

// 管道 → Socket
splice(
    pipefd[0],
    nullptr,
    socket_fd,
    nullptr,
    size,
    SPLICE_F_MOVE
);
```

数据逻辑流程是：

```
文件页缓存
    │
    │ 移动或引用内存页
    ▼
管道缓冲区
    │
    │ 移动或引用内存页
    ▼
Socket
```

### 5、tee()

`tee()` 用来在两个管道之间复制数据。

```
ssize_t tee(
    int fd_in,
    int fd_out,
    size_t len,
    unsigned int 
flags
);
```

它要求：

```
fd_in  必须是管道读端
fd_out 必须是管道写端
```

`tee()` 的作用不是移动数据，而是把同一批管道数据引用复制到另一个管道。

原管道中的数据不会被消费。



splice：转交数据引用（可以类比cpp的move，会消费输入管道中的数据，把对内存页的引用转交给另一个内核缓冲区）

 tee：复制数据引用（类比cpp的浅copy）

调用 `tee()` 后：

```
             ┌── 管道 A 引用
同一个数据页 ┤
             └── 管道 B 引用
```

管道 A 和管道 B 引用的是同一份实际数据，没有重新复制数据内容。

当然了这里只是大概可以这样理解，其中原理完全不同。

# 冯.诺依曼结构

冯.诺依曼提出了计算机“存储程序”的计算机设计理念，即将计算机指令进行编码后存储在计算机的存储器中，需要的时候可以顺序地执行程序代码，从而控制计算机运行，这就是冯.诺依曼计算机体系的开端。

核心设计思想主要体现在如下三个方面：

- 程序、数据的最终形态都是二进制编码，程序和数据都是以二进制方式存储在存储器中的，二进制编码也是计算机能够所识别和执行的编码。（可执行二进制文件：.bin文件）
- 程序、数据和指令序列，都是事先存在主（内）存储器中，以便于计算机在工作时能够高速地从存储器中提取指令并加以分析和执行。
- 确定了计算机的五个基本组成部分：运算器、控制器、存储器、输入设备、输出设备
